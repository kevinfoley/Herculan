# Handoff — mission editing in the HERCULAN Editor

Feasibility and scope for three features in the editor, `Herculan.Engine.Editor` (run on its own by `Herculan.Engine.Host.Editor`, and from the game's Editor menu item):

1. Showing and selecting the mission's non-object features — trigger areas, routes, groups, objectives and the action wiring between them.
2. Moving a herc to a new starting position.
3. Saving the edited mission back to `script.dat`.

## Headline

None of this is a from-scratch build. `MissionLoader` resolves almost every mission feature the editor could show into `Mission`, and the editor already shows and selects trigger areas, routes, the mission box, groups, objectives, timers and the action wiring ([In place](#in-place)); what is left of the first feature is the same kind of drawing and UI work. The `script.dat` writer exists and is complete: `ScriptDatTransformer.Write` covers all 13 blocks, and `HercWorks.UI.MissionScriptForm` already drives it through an open/edit/Save As UI. The editor keeps the parsed document (`EditorMission.Document`) beside the scene loaded from it, moves roster objects, route waypoints and groups in it, adds structures to it and deletes objects from it ([In place](#in-place), "Moving objects, waypoints and groups", "Adding structures" and "Deleting objects"); what is left of editing is moving area corners through the same machinery and a Save. Building a mission from nothing needs much more: the `.MSN` as the editor's document ([Holding the `.MSN` as the document](#holding-the-msn-as-the-document)), a new-mission path, and the creation and field editing of every record kind ([Authoring a mission from scratch](#authoring-a-mission-from-scratch)).

Whether DBSIM can read a grown file is settled (it can — [gap 2](#2-three-consequences-of-appending)).

## What already exists

- `Mission` carries `Actions` (each `MissionAction` with its resolved `MissionTriggerArea` list), `ActionTimers`, `GroupOrders` (each order's `Route` resolved to points), `PlayerRoute`, `Objectives`, `GroupDeploymentActions`, `GroupKinds`, `GroupSides`, `GroupOutOfActionReports`, `Coordinates` and `Text`. Each `MissionPlacement` carries its `GroupIndex`, `SlotIndex`, `EngagementActionRef`, `DefeatActionRef`, `StartingCondition` and `OutOfActionReport`.
- `SceneItem.Visible`, for hiding waiting groups; the editor's own `GroundPick`.
- `MissionLoader.AddRoster` — `Coordinate(script, record.PositionRef) ?? OffsetFromGroup(...)`. The engine honours a roster record's own position override, matching `Mech_AttachToGroup` (`00417aa8`), and the editor's object moves write it.
- `MissionPlacement.Kind` + `SlotIndex` address a block-7/8/9 record exactly, and `GroupIndex` addresses block 11, so the editor's selection already identifies the record to edit.
- `HercWorks.UI.MissionScriptForm.OnSaveAs` — a working save path, with VOL entry-prefix preservation and an advisory cross-block ref-range validator.
- `MissionGenerator` (Core) builds a `script.dat` from an `.MSN` as VSHELL does, and `MissionFileTransformer` round-trips `.MSN` files.
- `HercWorks.Query actions|orders|objectives` — the corpus cross-check for anything the editor shows.
- `MissionLoader.Load(content, script, path)` loads from a `ScriptDat` already parsed, which `EditorMission.Open` reads once and keeps as `Document`; the mission check runs over that document.
- Round-trip coverage: `TrainingLaunchTests.LoadsEveryRetailMission` writes a `script.dat` from each of the 62 `.MSN` files and checks `ScriptDatTransformer` rewrites it byte-exact, and `ScriptDatRoundTripTests` rewrites the install's `DATA\script.dat` and every `sav\script%d.dat` as a prefix of the file read (they keep stale tails past block 13). Both skip silently without an install.

## What a saved `script.dat` reaches

VSHELL writes `data\script.dat` afresh from the `.MSN` every time it loads a campaign or practice mission, and so does this engine's own campaign launch (`ShellCampaignLaunch`, through `MissionGenerator`). An edited `script.dat` is therefore played by: the editor and `Herculan.Engine.Host` opening that file directly; DBSIM run directly over `data\`; and a save slot, since `Career_LoadSlot` (`00412bbf`) copies `sav\script%d.dat` into `data\` and the replay flies it as-is ([`../retail/formats/save-games.md`](../retail/formats/save-games.md#the-slot-handoff)). It does not change a campaign mission. That needs the editor to hold the `.MSN` ([The `.MSN` layer](#the-msn-layer)).

## Mission features to show and select

Counts below are over the 62 retail `.MSN` files with campaign conditions not applied (`HercWorks.Query`).

### In place

- **Opening a mission.** The editor starts on `DATA\script.dat` or the file named on its command line, and with no mission and the VOL list up when there is none. File > Load from VOL lists every `.MSN` in the archives and opens one through `MissionFileLaunch` (the simulator host's `.MSN` path), generating the handoff into `%TEMP%\herculan-editor\` so the install's `DATA\` is never written; `EditorMission` and `MissionDrawables` are rebuilt for it. Such a mission's `Mission.SourcePath` is that scratch file, so a future Save must offer Save As for it rather than writing in place.
- **Selection and panels.** `EditorSelection` is an object, group, trigger area, action, timer, route (with an optional waypoint) or objective, held in one `SelectionState` that the viewport click, the `MissionOutliner` (left: groups with members, areas, actions, timers, routes, objectives under the block-13 briefing list) and the `PropertiesPanel` (right, one view per kind, every mentioned record a link) all set.
- **Camera.** `EditorCamera` flies free (right mouse to look, WASD/arrows, Q/E, Shift). A double-click in the viewport or the outliner selects and frames the selection (`SelectionBounds`, `EditorCamera.Frame`), keeping the yaw and looking down on it. V, or View > Top-down, switches to a view looking down from above, north up, high enough over the middle of the zone that its whole grid fits the window; there looking turns about the vertical alone, W is up the screen, fog is off and the clip planes are pushed out with the camera's height. V again returns to the pose it left; opening another mission leaves it.
- **Picking.** `ScenePicker` tries a waypoint in screen space, then an object's bounding sphere (skipping waiting groups when they are hidden), then `GroundPick` (a ray march against `HeightAtWorld`) and the smallest trigger area containing that ground point.
- **Overlays.** `MissionOverlay` draws, through `DrapedLines`, every trigger area (coloured by who trips it), every route (the player's, the walked ones and the never-walked ones in three colours, loops closed, waypoints numbered when selected), every base pad's painted tile (`MissionBasePad.TileOrigin`, with the selected group's authored point and its snap drawn too) and the mission box with its HDD-map and abort margins, each toggled from the View menu. A line hidden behind terrain shows dimmed. A selected area's ground is tinted yellow over exactly what its test catches — a circle area's octagon included — through `SceneRenderer.Highlight`, compiled only into the editor's program as the grid is.
- **Wiring.** `MissionIndex` cross-references, once, which actions test each area, which groups walk or merely name each route, and for each action the timers, engaged and defeated objects that fire it and the waiting groups, ended orders, started timers, counters and message (from `COMMAND<n>.STR`) that follow. The action view shows all of it, and an area's view shows it for every action testing that area.
- **Groups.** `Mission.GroupSetups` carries each block-11 record's point (with its pre-snap authored point and where it came from), heading (and whether it is the route bearing), formation id and paints-ground flag. Selecting a group boxes its members, highlights the route it walks, and `GroupOverlay` draws a post at its point, a heading arrow, and a line to each order's subject labelled with the slot and verb. Its view adds the setup, the out-of-action counter writes and the objectives asked of it to the members, deployment action and ten orders; an object's view adds its own counter writes and objectives.
- **Waiting groups.** View > Waiting Groups draws, outlines (meshes hidden, members boxed, still selectable) or hides the members of a group gated on an action. Unless hidden, each is labelled at its point with the action and the arrival (drop pod, on foot, in place), labels sharing a point stacked.
- **Mission check.** `ScriptDatLint` (Core) holds `MissionScriptForm`'s ref-range checks plus an action area ref behind its first `-1`, an objective condition or subject kind with no case, a group with neither a heading nor a slot-0 order, a herc group with no slot-0 order, and rosters past DBSIM's slot caps. Both apps run it; the editor lists the findings under Problems, each selecting its record, and `HercWorks.Query lint` runs it over every retail mission's generated `script.dat`, finding nothing.
- **Moving objects, waypoints and groups.** Selecting a roster object (not one of the player's squad, which has no roster record) shows typed X and Y fields in its view, and Z for a flyer, the one height the spawn pass reads from the point ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 5); a field applies when it loses the focus. In the viewport `MoveGizmo` draws X and Y arrows, a square in the ground plane between them and, for a flyer or a flyer group, a Z arrow, on the selected object, waypoint or group; dragging one previews the move and commits it on release. `PointMover` makes each edit. An object is given a point of its own: `ScriptPointRefs.Place` (Core) rewrites its point in place when nothing else names it (`ScriptPointRefs.Count` covers every block-1 ref) and appends one otherwise, and the sim object stands where the simulator would stand it. A waypoint moves the point it names, so whatever shares that point moves with it ([gap 1](#1-positions-are-indirect)); Alt+drag detaches it instead, through `ScriptPointRefs.Place` as for an object. Either way its point is written with Z 0, and a closed route's first and last waypoints move together. A group moves the same way through the point it stands on, its block-11 record's own or else its route's first waypoint (rules 2 and 3), so the route's start and whatever shares the point move with it; Alt+drag gives the record a point of its own. Its handles sit on its authored point, which a paints-ground structure group's snap then puts in its tile, so its pad jumps a tile at a time; its members with no point of their own follow, the player's squad with group 0. Only a flyer group's Z is written from the drag, and any other keeps its point's Z; the group view says what else names the point. After every change to block 1, `PointFollowers` places again from the document whatever stands on a moved point ([gap 4](#4-live-scene-refresh)), `MissionDrawables.Move` and `ScenePicker.Move` following each object it moves, and the route view says how many other records name the selected waypoint's point. The mission box overlay is rebuilt from block 1. After every move, a drag's preview included, `TerrainLeveller` puts the heightmap and the cell materials back as the zone loaded them and runs the spawn pass's pad painting and footprint flattening again over every structure and base pad where they now stand, so the ground and a pad's paint follow as they move and return to the zone as loaded where they leave; structures and walking mechs are settled on the new ground, the changed rows of the terrain mesh are rebuilt and uploaded, and the overlay lines are laid again. Edit > Undo and Redo (Ctrl+Z, Ctrl+Y) step through the edits. The view says when the object is outside the mission box as opened, and when it is a group follower that holds formation on its leader once the mission runs.
- **Adding structures.** The Toolbox window (`StructureToolbox`) lists the 45 structure types of `BASES.DAT` under the names the MFD status screen prints for them, with a Human or Cybrid choice for the side. An entry dragged out and let go over the view adds that structure on the ground under the pointer; a double-click, or Add with an entry chosen, adds it on the ground at the middle of the view, or under the camera when that is sky, which the gamepad's pointer reaches as well. While an entry is dragged over the view, the structure it would add stands on the ground under the pointer (`DropPreview`, drawn but not picked, listed or levelled under). Letting go over a panel adds nothing. With a structure group or one of its structures selected, "Join the selected group" adds the structure to that group instead: its record names a point of its own where it was put, it takes the group's first free member slot of the 20 (DBSIM walks them by raw index, [`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule) rule 7) and the group's side, and names no heading, so it faces the group's way. Otherwise `StructurePlacer` appends a block-9 record naming no point, heading or action of its own, pristine and writing no counter, and a block-11 group of its own with it in slot 0, standing on a block-1 point appended at the ground's height and facing a block-2 heading of 0 degrees (one already in the block is shared), in formation 0, not painting its ground, with no orders, no deployment action and no counter writes. That is the shape of 148 of the retail missions' 537 structure groups (`HercWorks.Query orders`), and the mission check passes it, since a group naming a heading needs no slot-0 order. An add that would take block 9 past DBSIM's 140 structure slots is refused, and the Toolbox says why. The object is built by `MissionScene.CreateObject`, the scene load's own path, its model built and uploaded then when nothing else in the mission draws with it; it joins `MissionIndex` with its group (`Mission` stays as loaded), the picker and the drawing, the ground is levelled under it as after a move, and it is selected. The add is one step of the undo history: Undo takes the records, the group, the object and its drawing out again, and Redo puts the same ones back. An added structure and its group move as any other.
- **Changing sides.** An object's view and a group's view offer Human or Cybrid for the group's side (block 11 `0x6e`), every group but the player's squad; the side is the group's, so all its members change, and the view says how many when there are others. `SideChanger` writes the field, the index's copy and each member's simulation object, as one step of the undo history.
- **Deleting objects.** An object's view has a Delete button, and the Delete key deletes the selected object unless a text field has the keyboard or a drag is under way; either clears the selection. It works on a structure, a mech or a flyer, loaded or added from the Toolbox, a waiting group's member included. `ObjectDeleter` unlinks the object rather than removing its record: every block-11 member ref naming its roster slot is set to `-1`, so DBSIM never spawns the record ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 1), and nothing is renumbered. A structure's first out-of-action operation is set to 0 too, as the briefing map shows a structure no group names by that operation ([`../retail/shell/mission-map.md`](../retail/shell/mission-map.md#what-it-reads)). The object leaves `MissionIndex`, the picker and the drawing, and the ground is levelled again without it. The view refuses, saying why with links: the player's squad; an objective's subject, an action's target, an order's subject, or an object firing an action of its own when engaged or defeated; and the last member of a group, since DBSIM does not run a group with no members safely (rule 1 there), unless that group is one the editor added, still block 11's last record and named by nothing, which the delete then removes with it, renumbering nothing. The delete is one step of the undo history: Undo links the object again and puts it back where it stood, and Redo unlinks it again.
- **Objectives and timers.** An objective's view gives mandatory or failure, the subject (boxed in the scene), the condition, for condition 0 the route (highlighted) and the subject group's first order slot on it, the `mission.str` failure text and the counter writes. A timer's view gives the delay, the action that starts it and the actions it fires, and the action view links to it.

### Gaps in what is in place

- **Waypoint height.** A moved waypoint's point is written with Z 0, as 1487 of the 1488 retail waypoints have it. DBSIM reads a waypoint's Z as the starting altitude of a flight standing on its route's first waypoint, and the heads-down map projects the player's route icons with it ([`../retail/simulation/ai-goals.md`](../retail/simulation/ai-goals.md#the-route-cursor-is-loaded-once)); everything else works in the ground plane. A waypoint has no field or handle for it; only a flyer group standing on its route's first waypoint sets it, through the group's Z handle. This engine's heads-down map places route icons by X and Y alone.
- **Waypoint and group views.** The route view lists its waypoints' coordinates and the group view its point read-only, with no typed fields as an object's view has, and neither warns when a waypoint or a group is moved outside the mission box as opened, though that grows the box and the heads-down map's frame as an object does (the box overlay shows it).
- **Area tint.** Only a selected area is tinted. A selected action's areas are outlined, not tinted: `SceneRenderer.Highlight` holds one region. The tint is painted on the terrain alone, not on a structure's ground plane (its shadow and floor plates) inside the area.
- **Adding.** Only structures can be added, and an added structure's type is fixed once it is added. A herc, a flyer or a ground vehicle (which drives, and whose group needs orders the Toolbox has no way to set) cannot ([Per row](#per-row)).
- **Deleting.** A group's last member cannot be deleted, except a just-added structure's own group while it is block 11's last record (so of two structures added one after the other, the first cannot be deleted while the second's group stands): that needs the group's block-11 record removed, every ref to a later group renumbered (objective and order subjects, action targets) and the index rebuilt. Nothing the mission names is deleted together with what names it. A deleted object's record stays in its roster, still counted against DBSIM's slot caps, and an add appends a record rather than reusing it.
- **Framing.** A double-click on a link in the Properties panel selects without framing. A timer stands nowhere and is not framed.
- **Top-down view.** It is the perspective camera at its pitch limit, 88 degrees down rather than 90, not an orthographic map: things stand up from the ground toward the edges of the view, and a point's place on screen shifts with its height. It frames the zone's grid as it opens, not whatever window size it is later resized to.
- **Ground planes from high up.** A structure's ground plane (shadow, floor plates) is ranked against the terrain by the cell `HeightGrid.PickDrawCell` files it under in the visible region, which `TerrainVisibleRegion.Update` keeps from the last view whenever the view's frustum, cut off at the zone's visibility range, reaches no ground, as it may from the top-down view's height. How the planes draw there has not been looked at.

Counts for the retail missions: 58 of 62 use trigger areas, 257 distinct areas named 143 times as boxes and 132 as circles, 16 shared by more than one action. Subjects are the player in 142 of 338 actions and the player's group in 170. `C2_01`'s boundary strips and `TRAIN8.MSN`'s three defeat-chained reinforcement waves ([`../retail/simulation/mission-deployment.md`](../retail/simulation/mission-deployment.md#train8msn-end-to-end)) are good test cases.

### Groups in the scene (blocks 10, 11)

Two things the group display still lacks. Ghosts of the formation slots a group leaves empty need the formation tables, which only `MissionLoader` holds. An order's own point (`+0x04`, set in 47 orders) is read only by the briefing map, and only off the squad's first order ([`../retail/simulation/ai-goals.md`](../retail/simulation/ai-goals.md#the-order-record)); mark it as a distinct briefing-only marker or leave it out.

Size: small each.

### Waiting groups as true ghosts

Outlining stands in for ghosting. Drawing the meshes translucent instead needs a tint or alpha path in `SceneRenderer`.

Size: small–medium.

### Action graph

The action view walks the wiring one link at a time; a node graph of the mission's actions, timers and the objects and groups between them would show it at once.

Size: medium–large.

### Left out

- **Drop-pod and on-foot arrival points.** Picked at run time relative to the player's position and heading when the action fires; nothing static to draw.
- **Detection and engagement ranges** (50,000 and 100,000 units). Simulation constants, not mission data; a per-object debug ring at most.
- **Variants and conditions.** `script.dat` is already resolved; these exist only in the `.MSN`, which the editor does not hold ([The `.MSN` layer](#the-msn-layer)).

## Gaps on the write path

### 1. Positions are indirect

An object does not hold a position; it holds a `PositionRef` index into block 1. Most retail roster records carry `-1` there, so the object inherits its group's point plus a formation offset ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 2, gives the ones that name their own), and moving one gives it a point of its own. `ScriptPointRefs.Place` appends one, which shifts nothing since every other block names block 1 by array position, or rewrites it in place once the record is its only user. It does not look for an identical existing point to reuse: file length is not a constraint.

Points are shared on purpose. In 45 of the 62 retail missions a route waypoint is the same block-1 point as a trigger area's center or corner (94 of the 886 distinct waypoint points, from `HercWorks.Query routes` and `actions`): that is how a mission fires an action when a waypoint is reached. `C1_01`'s player route runs through points 119, 121, 122, 123 and 124, its drop-pod triggers are circles about 121 to 124, and the groups those triggers bring in deploy on 119. So a waypoint drag moves the shared point, and the trigger and the groups move with it; giving the waypoint a point of its own, which Alt+drag does, leaves them where they were. A group drag (block 11) makes the same choice the same way, and moving an area corner (block 4) directly will meet it too.

### 2. Three consequences of appending

- **Block 1's extent frames the heads-down map** (see [`../retail/simulation/heads-down-display.md`](../retail/simulation/heads-down-display.md#the-maps-frame-of-reference), and `MissionBox`), and the mission box. A point outside the current box silently rescales the player's in-game map and moves the boundary warning and abort lines. The object view warns on it, and the mission box overlay is rebuilt after each edit.
- **File length is not a constraint.** `DBSim_LoadScriptDat` (`00424308`) reads through a `FileRStream` block by block and allocates each of blocks 1-6 and the group array from its own count, so a file longer than the retail 13,520 bytes reads correctly. Its fixed arrays are the per-roster slot flags and slot maps ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#the-two-pass-read--and-what-it-means-for-dbsim-keeps)); past them it writes over neighbouring globals. Appending block-1 points is unaffected; adding roster records is not: the mission check reports a roster past its cap, and the editor refuses to add a structure past block 9's. Appending does give meaning to a ref past block 1's old end, which then names the appended point; the mission check reports such refs, and no retail mission has one, but the editor does not re-run the check after an edit ([gap 4](#4-live-scene-refresh)). VSHELL's own reader, `ShellMap_LoadScriptDat` (`004243d7`), has not been checked for caps, and it reads a save slot's file for the briefing map.
- **A mech's or flyer's own point has never been observed live.** No retail mech or flyer record names one ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 2), so `Mech_AttachToGroup` and `Flyer_AttachToGroup` honouring it is RE-derived and engine-implemented, and the editor's moves of either rely on it. Structures' is exercised by retail data. Confirming it means writing such a file and running retail DBSIM.

### 3. Moved is not the same as stays there

- `MissionPlacement` carries `FormationOffset` even when the record supplies its own position, and AI followers hold formation on their leader every tick. For a non-leader group member the edit sets a spawn position the AI may walk out of; the object view says so.
- A group with no point of its own stands on its route's first waypoint, so moving that waypoint, as a plain group drag does, moves the start of the route too. Given a point of its own (Alt+drag), it spawns there instead, its route unchanged.
- A paints-ground base group snaps to a fixed spot in its tile, so a small move does nothing and a larger one jumps a whole tile ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#the-anchor)); the base pad overlay shows the tile.
- A group waiting to deploy by drop pod or on foot is placed at a placeholder, so moving it changes nothing once the mission runs ([`../retail/simulation/mission-deployment.md`](../retail/simulation/mission-deployment.md#arrival--group_deploymentcheck-004236c4)); its view says so. One arriving in place, and a held-back structure, stand where they are placed: the structure, solid and undrawn, from the first frame ([`../retail/simulation/mission-deployment.md`](../retail/simulation/mission-deployment.md#held-back-structures-stand-from-the-start)).

### 4. Live scene refresh

An object move re-places that object's items and pick sphere. After every change to block 1, `PointFollowers` places again, by the loader's rules, whatever stands on a point that moved: route points, trigger areas, each group's point and heading (its own point, else its route's first waypoint, facing along the first leg when it names no heading) with the members spread from it, a paints-ground group's pad outline, and objects whose roster record names the point. The positions it moves are editor copies in `MissionIndex`; `Mission` and the mission check stay as loaded (a `MissionPlacement.Position`, the orders' routes and the actions' areas go stale, and nothing in the editor reads a position from them). The ground is levelled and the pads painted again where the structures and pads now stand (`TerrainLeveller`).

## Authoring a mission from scratch

Everything in [In place](#in-place) moves something, changes a group's side, or adds or unlinks a structure; every other field of every record is shown read-only or not at all. This is what building a mission from nothing needs beyond that.

### The `.MSN` layer

The editor's document is the `script.dat` VSHELL writes once it has filtered and resolved the `.MSN`, and opening a VOL mission generates one. What the `.MSN` holds beyond that has no place in the document:

| `.MSN` part | What it carries |
|---|---|
| [Row 1](../retail/formats/msn-mission-file.md#the-conditions--row-1) | the campaign-flag comparisons and random draws every record's condition names |
| [Row 2](../retail/formats/msn-mission-file.md#the-header-patch--row-2) | the header words, patched by condition, and flags to clear |
| Row 3 | the briefing and debrief movie ids |
| Row 4 | the objective, briefing and intelligence lines and the briefing movie. `script.dat` keeps only the objective lines, as block 13, which the outliner lists read-only |
| [Row 5](../retail/formats/msn-mission-file.md#row-5--the-debrief) | the debrief lines and movie |
| [`.ENG`](../retail/formats/msn-mission-file.md#the-eng-string-table) | every line of the mission's text, with conditioned replacements. The editor reads `mission.str`, already resolved, and edits none of it |
| [Variants](../retail/formats/msn-mission-file.md#variants) and [repeated GUIDs](../retail/formats/msn-mission-file.md#repeated-guids) | random alternatives and condition-dependent overrides, resolved before `script.dat` is written |
| GUIDs | how `.MSN` records name each other, where `script.dat` names by array position |

A mission the shell loads, practice or campaign, is an `.MSN`. A practice mission needs at least row 2's header, row 4's text, group 0's row-12 squad and the `.ENG`; a campaign mission uses rows 1, 3 and 5 and variants too. A mission authored from nothing therefore needs an `.MSN` model in the editor, whatever a `script.dat` save does.

### Holding the `.MSN` as the document

What it takes to make the `.MSN` and its `.ENG` the editor's document, with `script.dat` a view generated from them after each edit. Paths are under `src/HercWorks.Core/` unless named otherwise.

**The model.** `MissionFile` (`Data/File/Msn/MissionFile.cs`) holds all 17 rows, and `MissionFileTransformer` reads and writes them in file order (`Io/Transform/Common/MissionFileTransformer.cs:11-45`, `:312-340`). Rows 1, 3, 4 and 6 to 17 are typed records whose fields are settable properties (`:57-306`), every GUID-keyed one a `MapObject` with a settable `GUID` (`Data/File/Msn/MapObject.cs:7-10`). Row 2 is a raw `short[41]`, `MissionSettingsPatch.Data` (`Data/File/Msn/MissionSettingsPatch.cs:31-33`): its layout (a condition, ten header words, thirty flag indices) is what the generator reads (`Io/Transform/Common/MissionGenerator.cs:345-378`), but nothing names the words. Row 5 is raw bytes, `MissionFile.DebriefBytes` (`MissionFile.cs:33`, transformer `:27-28`): the debrief reload reads each 32-word record as a condition, thirty text refs and a row-3 ref (`MissionGenerator.cs:150-179`), and no type does. Inside the typed rows some spans stay unnamed words or arrays (`Unk04`, `Unk06`, `Unk1A`, row 12's and row 16's `DeadZone`, row 13's `FlagSpan`), and row 10's counter pairs are a flat `short[20]`. The `.ENG` is `MissionStringFile`, its entries settable (`Data/File/Msn/MissionStringFile.cs:44-72`), and its writer takes each length from the text (`Io/Transform/Common/MissionStringFileTransformer.cs:36-55`). `HercWorks.Query census` round-trips all 62 `.MSN` and all 62 `.ENG` files in `ZONES.VOL` byte for byte, `DEMO2.MSN`'s truncated row 17 included (a null in `MissionFile.Objectives`, `MissionFile.cs:68-78`). A row is a fixed array, so adding a record replaces the row's array, as `ScriptDat`'s blocks are replaced today. `MissionFile`'s lookups (`GetPoint`, `GetMech` and the rest, `MissionFile.cs:80-108`) ignore conditions and variants and merge no overlays, so they are not what a mission resolves to; only the generator gives that.

**Provenance.** `MissionGenerator.Load` takes the `.MSN` as bytes, not a `MissionFile` (`MissionGenerator.cs:103`), and walks them with its own cursor, so an edited `MissionFile` is written before it is generated from. Both read the rows in the same order, so the loop counter of each `Read…` method is the record's index in `MissionFile`'s row array, a record that fails its condition included. `MissionGenerator.Provenance`, a `MissionProvenance` (`Io/Transform/Common/MissionProvenance.cs`), is told by the generator as it adds, replaces, overlays and variant-copies, and answers which records supplied what it writes. `Slot(block, index)` gives an exported `script.dat` record's `SlotProvenance`: the `MsnRecordId` (row and index) that created the slot, the records merged into it in read order, each `VariantCopy` (the record that asked, the source it copied from and the words covered), and `Word(word)`, per `.MSN` word, a `WordSource` naming the record whose write the slot holds and, for a copied word, the variant source it was authored in. `ExportedSlot(record)` is the reverse, the `ScriptDatSlot` a record created or was merged into, null for a record that failed its condition, has GUID `-1` or is a variant source. `Lines` and `LineOf(engRecord)` do the same for `mission.str` lines: the `.ENG` record that placed each and the one whose text it holds. It covers blocks 1 to 12, block 13 as row 4's slot 0, and every `mission.str` line; row 2's header patches and row 3's values, which reach only the header and the row-4 and row-5 movie ids, are not traced, and a row-6 point with its sum flag set reports its coordinates as its own record's. Row 8's word 4 stands for its waypoint count and list together. It changes nothing the generator writes, which its reproduction of two retail TRAIN5 handoffs keeps checked.

**Conditions and variants.** Every record passes `Gate` (`:251-263`) against the row-1 survivors. Row 1's type 0 compares the caller's flag array (`:200-208`), type 1 draws from the caller's roll (`:210-215`) and type 2 tests its parent's draw (`:217-222`); `PickVariant` draws again for every record that asks, in file order (`:290-312`). Row 2 zeroes flags in the caller's array and writes into the caller's clear list (`:345-378`), so each generation needs fresh copies of both. The editor's VOL open goes through `MissionFileLaunch.Write` (`src/Herculan.Engine/Shell/MissionFileLaunch.cs:67-115`): a practice mission's flags are cleared and flags 3 to 6 seeded (`ShellTrainingLaunch.SeedDrawnFlags`), a campaign mission's start empty and take the career position's seed, and every draw comes from `ShellTrainingLaunch.StartupRandom`, seeded from the tick count (`src/Herculan.Engine/Shell/ShellTrainingLaunch.cs:41-48`), so opening the same mission twice can pick different variants. A practice load then overwrites header words 0 and 5 to 9 with the practice options (`ShellTrainingLaunch.cs:133-139`), and a regeneration has to do the same. `HercWorks.Query lint` uses zero flags and a roll of 0 throughout (`src/HercWorks.Query/LintQuery.cs:22-23`).

The proposed default: the flags the VOL open builds, a fresh clear list, and draws from a `SimRandom` on a seed the document keeps, recreated for every generation, so each regeneration draws the same sequence and nothing in the scene reshuffles on an edit; a command picks a new seed, and a flag-state choice can come later. Draws are made in file order, row 1's type-1 records first, then each variant-keyed record of rows 8, 12, 13 and 14 as it is read (the keys of rows 6, 7 and 15 are `-1` in every retail file). An edit that appends records with no variant key, as every add does, leaves every draw as it was; deleting a keyed record, or adding a draw ahead of others, moves the draws after it. A roll of 0 throughout is stable under every edit but shows one outcome only.

An edit writes the record that supplied the value in the editor's state:

| The `script.dat` value came from | The edit writes |
|---|---|
| a row-3, 6, 7, 8 or 9 GUID carried by more than one surviving record (replace) | the last surviving record of the GUID, whose payload the slot holds. 451 row-6 GUIDs in 24 missions are carried by two or more unconditioned records (`HercWorks.Query repeats`) |
| a row-10 to 16 GUID carried by more than one surviving record (overlay) | per field, the last surviving record of the GUID that sets it, else the first |
| a field of rows 12 to 15 copied from a variant | not the source, a GUID `-1` alternative shared by every record that can draw it, but an unconditioned record of the same GUID appended to the row, carrying that field alone, which overlays it whatever is drawn |
| a row-8 waypoint list copied from a variant (2% of retail routes) | either the alternative, moving every route that draws it, or the route detached: its key set to `-1` and its own list written. Row 8 replaces rather than overlays, so an appended record cannot carry one waypoint |
| a field set to its unset value (a member slot to `-1`) | every record of the GUID that sets the field, whatever its condition: an overlay cannot carry an unset value |

A supplier with a condition holds the edit only in the states it survives in, and the view has to say so. Counting what shares a point counts every record naming its GUID, whatever its condition, since one conditioned out in the editor's state names it in another.

The deleter becomes simpler: it removes rather than unlinks, needs no briefing-map write, and removes any group, so the [Deleting](#gaps-in-what-is-in-place) gap closes. The placer loses its index arithmetic. The mover and the shared-point count gain the supplier lookup and the variant overlay. The side change is the same size.

**Regenerating on each edit.** A committed edit writes the `MissionFile`, keeping the records it replaced for undo, then writes the file, generates from it and parses the output as a `ScriptDat`. Everything that reads the document today (`PointFollowers`, `MissionLint`, the tools' own checks) holds the `ScriptDat` it was built with (`PointMover.cs:71`), so the generated blocks are copied into that object or reach the readers through one holder. Writing, generating and parsing touch arrays of a few hundred records; the scene's terrain and models are not reloaded. When the generated blocks keep every record where it was (a move, a side change, an add that appends), today's incremental scene updates apply as they are. A delete moves every later record of its block down one, so `Mission`, `MissionIndex` and each `MissionPlacement.SlotIndex` are rebuilt from the generated file, the scene objects kept by GUID provenance; `MissionLoader.Load(content, script, path)` already builds a `Mission` from a parsed `ScriptDat`. Save writes the `.MSN` and the `.ENG`, and a `script.dat` export is the generated one.

Size: medium for the document and the regeneration loop with its rebuild after a delete; porting the tools is small for `ScriptPointRefs`, `StructurePlacer`, `ObjectDeleter` and `SideChanger` each, and small–medium for `PointMover`.

Checked and not found:

- No `HercWorks.Query` report counts the row-10 to 16 GUIDs carried by more than one record; `repeats` covers rows 3 and 6 to 9. How often an overlay edit meets a conditioned supplier in retail is not counted.
- Whether every retail variant table has a child whose range holds a draw of 0 was not checked. A table with none makes `PickVariant` answer `-1` (`MissionGenerator.cs:306-311`), and a row-12 to 15 record that asked keeps its own refs unresolved (`:805-818`), which matters for a roll of 0.
- How long one write, generation and parse takes was not measured.
- The slot caps are checked against the file generated in the editor's state; no check covers the most records any flag state lets survive.

### Mission level

- **No new mission.** The editor opens an existing `script.dat` or a VOL `.MSN`; nothing starts an empty mission on a chosen zone.
- **The header** ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#header-format)) is not editable: theater, zone, day or night variant, objective type (offset 6, which picks the player's objective arm) and training mission number. The difficulty and the two training cheats are overwritten at every shell load.
- **The player's squad.** In the `.MSN` group 0's members are row-12 records, from which a practice load builds the player's machine and wingmen ([`../retail/shell/main-menu.md`](../retail/shell/main-menu.md#starting-a-practice-mission)). The editor treats the squad as fixed, so the player's chassis, weapon fit and wingmen cannot be set.

### Counters and caps

- **Mission counters.** Actions, objectives and out-of-action reports write counters, which persist into the campaign flags the next mission's row 1 tests ([`../retail/shell/campaign-loop.md`](../retail/shell/campaign-loop.md#the-campaign-flag-array-is-the-msn-condition-store)). Nothing lists which counters a mission writes, so nothing helps choose a free one or wire it to a condition.
- **Slot caps.** Adding mechs and flyers needs the refusal structure adds have, against `ScriptDatLint`'s 100 mech and 50 flyer slots.

## Suggested sequencing

1. The `.MSN` as the document, built on `MissionProvenance`, with the five edit tools ported to it, before more tools are built on `script.dat`'s positional refs.
2. Area-corner moves through the same point placement.
3. Save, which turns the edits into a file DBSIM can be run over.
4. The least a practice mission authored from nothing needs, in order: a new mission with its header, the player's squad, hercs added in groups with orders, routes, and objectives with their lines and failure text. Then trigger areas, actions and timers for scripted events, and the campaign layer (conditions, variants, debrief) last.
