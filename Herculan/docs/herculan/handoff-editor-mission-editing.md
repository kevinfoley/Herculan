# Handoff — mission editing in the HERCULAN Editor

Feasibility and scope for three features in the editor, `Herculan.Engine.Editor` (run on its own by `Herculan.Engine.Host.Editor`, and from the game's Editor menu item):

1. Showing and selecting the mission's non-object features — trigger areas, routes, groups, objectives and the action wiring between them.
2. Moving a herc to a new starting position.
3. Saving the edited mission.

## Headline

None of this is a from-scratch build. `MissionLoader` resolves almost every mission feature the editor could show into `Mission`, and the editor already shows and selects trigger areas, routes, the mission box, groups, objectives, timers and the action wiring ([In place](#in-place)); what is left of the first feature is the same kind of drawing and UI work. The `script.dat` writer exists and is complete: `ScriptDatTransformer.Write` covers all 13 blocks, and `HercWorks.UI.MissionScriptForm` already drives it through an open/edit/Save As UI. The editor holds a VOL mission as its `.MSN` and `.ENG` (`EditorMission.Source`, a `MissionDocument`), with the `script.dat` the scene is loaded from generated from them, and moves roster objects, route waypoints and groups, changes groups' sides, adds structures, deletes roster objects, fits the player's squad and adds and removes squadmates by writing the `.MSN` and generating again ([In place](#in-place), "Moving objects, waypoints and groups", "Adding structures", "Changing sides", "Deleting objects" and "The player's squad"; [Holding the `.MSN` as the document](#holding-the-msn-as-the-document)). A plain `script.dat` opens read-only. Save writes the `.MSN` and its text into the install, where the game loads them in place of the archive's ([In place](#in-place), "Saving"). What is left of editing is moving area corners through the same machinery. File > New mission starts a mission on a chosen zone, the player's machine alone with one nav point to reach ([In place](#in-place), "New mission"); building one up from there needs the creation and field editing of every record kind ([Authoring a mission from scratch](#authoring-a-mission-from-scratch)).

Whether DBSIM can read a grown file is settled (it can — [gap 2](#2-three-consequences-of-appending)).

## What already exists

- `Mission` carries `Actions` (each `MissionAction` with its resolved `MissionTriggerArea` list), `ActionTimers`, `GroupOrders` (each order's `Route` resolved to points), `PlayerRoute`, `Objectives`, `GroupDeploymentActions`, `GroupKinds`, `GroupSides`, `GroupOutOfActionReports`, `Coordinates` and `Text`. Each `MissionPlacement` carries its `GroupIndex`, `SlotIndex`, `EngagementActionRef`, `DefeatActionRef`, `StartingCondition` and `OutOfActionReport`.
- `SceneItem.Visible`, for hiding waiting groups; the editor's own `GroundPick`.
- `MissionLoader.AddRoster` — `Coordinate(script, record.PositionRef) ?? OffsetFromGroup(...)`. The engine honours a roster record's own position override, matching `Mech_AttachToGroup` (`00417aa8`), and the editor's object moves write it.
- `MissionPlacement.Kind` + `SlotIndex` address a block-7/8/9 record exactly, and `GroupIndex` addresses block 11, so the editor's selection already identifies the record to edit.
- `HercWorks.UI.MissionScriptForm.OnSaveAs` — a working save path, with VOL entry-prefix preservation and an advisory cross-block ref-range validator.
- `MissionGenerator` (Core) builds a `script.dat` from an `.MSN` as VSHELL does, and `MissionFileTransformer` round-trips `.MSN` files.
- `HercWorks.Query actions|orders|objectives` — the corpus cross-check for anything the editor shows; `records <MISSION> [--row N]` and `header <MISSION>` dump one mission's raw `.MSN` records, and row 2 beside the header it generates.
- `MissionLoader.Load(content, script, path)` loads from a `ScriptDat` already parsed: `EditorMission.Open` hands it the one a `MissionDocument` generated, or a plain file's as read, and keeps it as `Document`; the mission check runs over that document as opened.
- Round-trip coverage: `TrainingLaunchTests.LoadsEveryRetailMission` writes a `script.dat` from each of the 62 `.MSN` files and checks `ScriptDatTransformer` rewrites it byte-exact, and `ScriptDatRoundTripTests` rewrites the install's `DATA\script.dat` and every `sav\script%d.dat` as a prefix of the file read (they keep stale tails past block 13). Both skip silently without an install.

## What a saved `script.dat` reaches

VSHELL writes `data\script.dat` afresh from the `.MSN` every time it loads a campaign or practice mission, and so does this engine's own campaign launch (`ShellCampaignLaunch`, through `MissionGenerator`). A `script.dat` exported from the editor's generated one is therefore played by: `Herculan.Engine.Host` opening that file directly; DBSIM run directly over `data\`; and a save slot, since `Career_LoadSlot` (`00412bbf`) copies `sav\script%d.dat` into `data\` and the replay plays it as-is ([`../retail/formats/save-games.md`](../retail/formats/save-games.md#the-slot-handoff)). It does not change a campaign mission, which is the `.MSN`'s ([The `.MSN` layer](#the-msn-layer)); a Save of the `.MSN` does ([In place](#in-place), "Saving").

## Writing the editor's UI

What the user has corrected in the editor's panels, which every new view follows:

- **Vocabulary.** The player's group is the squad, never a "lance"; its other members are squadmates, never "wingmen". The player *pilots* a HERC; "fly" is for flyers. The subject of a sentence is the player, the mission or the HERC, never "the game" ("the game flies X" says nothing). A group's side is its **Team**. A structure or ground vehicle is titled by its type and the name the MFD's F5 screen prints (`Base type 40: <name>`).
- **Plain words, short.** A note says what the user sees or can do, in one short sentence, not how the records produce it: "No heading of its own: it faces along its route's first leg", not "names none: the bearing of its route's first leg". Labels are the user's words ("Related objectives", not "Objectives asked of it").
- **No note for what a disabled control already shows.** A field the user cannot change is drawn disabled; a note is added only when the reason is not obvious, and a note saying only that something cannot be changed is left out.
- **Notes go through `EditorText`.** `EditorText.Note` draws every aside wrapped, in a grey lighter than ImGui's disabled text, which the 340-pixel Properties panel cuts off unwrapped and which is hard to read. `EditorText.Emphasis` draws, in the bold face, the one note per view the user must not miss (a campaign mission's squad set here is not used).
- **Latin-1 only in UI strings.** The ImGui font atlas holds Basic Latin and Latin-1, so an em dash or a curly quote draws as `?`. Use parentheses, colons and straight quotes; `°` is in range.
- **Identity first.** An object's view opens with its name and then its group, before any other field.
- **Errors point at the fix.** A refused input shows its reason in a strong red and tints the field to change (the New mission dialog's name).

## Mission features to show and select

Counts below are over the 62 retail `.MSN` files with campaign conditions not applied (`HercWorks.Query`).

### In place

- **Opening a mission.** The editor starts on `DATA\script.dat` or the file named on its command line, read-only ("A plain `script.dat`" in [Holding the `.MSN` as the document](#holding-the-msn-as-the-document)), and with no mission and the VOL list up when there is none. File > Load from VOL lists every `.MSN` in the archives and every loose one in the install's `MSN\` folder, marking a loose one "(saved)" when it overrides an archive mission and "(new)" when no archive holds it, and opens one through `MissionFileLaunch.Open` (the simulator host's `.MSN` path), which writes the handoff into `%TEMP%\herculan-editor\`, so the install's `DATA\` is never written, and holds the mission as a `MissionDocument` whose generation draws what the handoff's load drew; the document's generated `script.dat` and `mission.str` are written over the handoff's, and the scene is loaded from them. `EditorMission` and `MissionDrawables` are rebuilt for it. Such a mission's `Mission.SourcePath` is that scratch file.
- **New mission.** File > New mission (`NewMissionDialog`) asks for a name, taken as Save As takes one but never an archive mission's, which the game would play as that mission in its career position, and asking first when the install has a saved mission of that name; a zone, from every `dat\ZONE*.DAT` with its `.DBA` in DBSIM's mount, each listed with the theaters the retail missions in it are played on (`MissionZones`: each mission's zone as its load writes the header, and the theater its launch writes over it, `MissionFileLaunch.LaunchTheater`); and day or night. `NewMission` (Core, `Data/File/Msn/NewMission.cs`) builds the `.MSN` and `.ENG`: the player's machine alone on a route of two points, with one mandatory objective met when the player reaches the second, every record copied from `TRAIN1.MSN` but the text package, which takes `TRAIN5.MSN`'s shape; its comments cite each record. `MissionFileLaunch.OpenNew` opens it from memory as `Open` opens a mission `gam\career.dat` does not list, as `INSTANT ACTION`, into the same scratch handoff, and the title carries `*` until File > Save writes it (`EditHistory.MarkNeverSaved`); the browser then lists it "(new)". That load writes theater 1 and the practice screen's time of day over the header, as for every practice mission ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#the-training-fields)), so the editor and the game show a new mission on theater 1 by the practice screen's day or night whatever the dialog chose; the dialog says so, and only the `.MSN` keeps the choice. The mission check finds nothing in it.
- **Selection and panels.** `EditorSelection` is an object, group, trigger area, action, timer, route (with an optional waypoint) or objective, held in one `SelectionState` that the viewport click, the `MissionOutliner` (left: groups with members, areas, actions, timers, routes, objectives under the block-13 briefing list) and the `PropertiesPanel` (right, one view per kind, every mentioned record a link) all set.
- **Camera.** `EditorCamera` flies free (right mouse to look, WASD/arrows, Q/E, Shift). A double-click in the viewport or the outliner selects and frames the selection (`SelectionBounds`, `EditorCamera.Frame`), keeping the yaw and looking down on it. V, or View > Top-down, switches to a view looking down from above, north up, high enough over the middle of the zone that its whole grid fits the window; there looking turns about the vertical alone, W is up the screen, fog is off and the clip planes are pushed out with the camera's height. V again returns to the pose it left; opening another mission leaves it.
- **Picking.** `ScenePicker` tries a waypoint in screen space, then an object (skipping waiting groups when they are hidden): the bounding spheres the ray meets give the candidates, and the nearest of their triangles it meets wins, a structure's ground plane counting only when it meets nothing solid, so a Herc on a base's pad is picked rather than the base; then `GroundPick` (a ray march against `HeightAtWorld`) and the smallest trigger area containing that ground point.
- **Overlays.** `MissionOverlay` draws, through `DrapedLines`, every trigger area (coloured by who trips it), every route (the player's, the walked ones and the never-walked ones in three colours, loops closed, waypoints numbered when selected), every base pad's painted tile (`MissionBasePad.TileOrigin`, with the selected group's authored point and its snap drawn too) and the mission box with its HDD-map and abort margins, each toggled from the View menu. A line hidden behind terrain shows dimmed. A selected area's ground is tinted yellow over exactly what its test catches — a circle area's octagon included — through `SceneRenderer.Highlight`, compiled only into the editor's program as the grid is.
- **Wiring.** `MissionIndex` cross-references, once, which actions test each area, which groups walk or merely name each route, and for each action the timers, engaged and defeated objects that fire it and the waiting groups, ended orders, started timers, counters and message (from `COMMAND<n>.STR`) that follow. The action view shows all of it, and an area's view shows it for every action testing that area.
- **Groups.** `Mission.GroupSetups` carries each block-11 record's point (with its pre-snap authored point and where it came from), heading (and whether it is the route bearing), formation id and paints-ground flag. Selecting a group boxes its members, highlights the route it walks, and `GroupOverlay` draws a post at its point, a heading arrow, and a line to each order's subject labelled with the slot and verb. Its view adds the setup, the out-of-action counter writes and the objectives asked of it to the members, deployment action and ten orders; an object's view adds its own counter writes and objectives.
- **Waiting groups.** View > Waiting Groups draws, outlines (meshes hidden, members boxed, still selectable) or hides the members of a group gated on an action. Unless hidden, each is labelled at its point with the action and the arrival (drop pod, on foot, in place), labels sharing a point stacked.
- **Mission check.** `ScriptDatLint` (Core) holds `MissionScriptForm`'s ref-range checks plus an action area ref behind its first `-1`, an objective condition or subject kind with no case, a group with neither a heading nor a slot-0 order, a herc group with no slot-0 order, and rosters past DBSIM's slot caps. Both apps run it; the editor lists the findings under Problems, each selecting its record, and `HercWorks.Query lint` runs it over every retail mission's generated `script.dat`, finding nothing.
- **Moving objects, waypoints and groups.** Selecting a roster object (not one of the player's squad, which has no roster record) shows typed X and Y fields in its view, and Z for a flyer, the one height the spawn pass reads from the point ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 5); a field applies when it loses the focus. In the viewport `MoveGizmo` draws X and Y arrows, a square in the ground plane between them and, for a flyer or a flyer group, a Z arrow, on the selected object, waypoint or group; dragging one previews the move and commits it on release. `PointMover` makes each edit: the commit writes the `.MSN` and generates `script.dat` again ("The tools" in [Holding the `.MSN` as the document](#holding-the-msn-as-the-document)), and a drag's preview writes the generated `script.dat` alone. An object is given a point of its own: `MissionDocument.PlacePoint` rewrites its row-6 record in place when the object's field is all that names that GUID, in any record, and the GUID has one record, and appends a point with a new GUID otherwise, which the roster record that supplies the field then names; the sim object stands where the simulator would stand it. A waypoint moves the point it names, so whatever shares that point moves with it ([gap 1](#1-positions-are-indirect)); Alt+drag detaches it instead, through `MissionDocument.PlacePoint` as for an object, its route's list entry naming the point placed; a list a variant supplies is the alternative's, which every route drawing it shares. Either way its point is written with Z 0, and a closed route's first and last waypoints move together. A group moves the same way through the point it stands on, its block-11 record's own or else its route's first waypoint (rules 2 and 3), so the route's start and whatever shares the point move with it; Alt+drag gives the record a point of its own. Its handles sit on its authored point, which a paints-ground structure group's snap then puts in its tile, so its pad jumps a tile at a time; its members with no point of their own follow, the player's squad with group 0. Only a flyer group's Z is written from the drag, and any other keeps its point's Z; the group view says what else names the point. After every change to block 1, `PointFollowers` places again from the generated document whatever stands on a moved point ([gap 4](#4-live-scene-refresh)), `MissionDrawables.Move` and `ScenePicker.Move` following each object it moves, and the route view says how many other `.MSN` records name the selected waypoint's point. The mission box overlay is rebuilt from block 1. After every move, a drag's preview included, `TerrainLeveller` puts the heightmap and the cell materials back as the zone loaded them and runs the spawn pass's pad painting and footprint flattening again over every structure and base pad where they now stand, so the ground and a pad's paint follow as they move and return to the zone as loaded where they leave; structures and walking mechs are settled on the new ground, the changed rows of the terrain mesh are rebuilt and uploaded, and the overlay lines are laid again. Edit > Undo and Redo (Ctrl+Z, Ctrl+Y) step through the edits, each putting back the `.MSN` rows it changed and generating again. The view says when the object is outside the mission box as opened, and when it is a group follower that holds formation on its leader once the mission runs.
- **Adding structures.** The Toolbox window (`StructureToolbox`) lists the 45 structure types of `BASES.DAT` under the names the MFD status screen prints for them, with a Human or Cybrid choice for the side. An entry dragged out and let go over the view adds that structure on the ground under the pointer; a double-click, or Add with an entry chosen, adds it on the ground at the middle of the view, or under the camera when that is sky, which the gamepad's pointer reaches as well. While an entry is dragged over the view, the structure it would add stands on the ground under the pointer (`DropPreview`, drawn but not picked, listed or levelled under). Letting go over a panel adds nothing. With a structure group or one of its structures selected, "Join the selected group" adds the structure to that group instead: its record names a point of its own where it was put, it takes the group's first member slot of the 20 that no record of the group's GUID fills in any state (DBSIM walks them by raw index, [`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule) rule 7) and the group's side, and names no heading, so it faces the group's way. Otherwise `StructurePlacer` appends to the `.MSN` a row-14 record naming no point, heading or action of its own, pristine and writing no counter, and a row-16 group of its own with it in slot 0, standing on a row-6 point appended at the ground's height and facing a row-7 heading of 0 degrees (a lone unconditioned row-7 record reading 0 is shared), in formation 0, not painting its ground, with no orders, no deployment action and no counter writes; each record is unconditioned, with a new GUID. That is the shape of 148 of the retail missions' 537 structure groups (`HercWorks.Query orders`), and the mission check passes it, since a group naming a heading needs no slot-0 order. An add that would take block 9 past DBSIM's 140 structure slots is refused, and the Toolbox says why. The editor's state is then built again from the generated file ("Rebuilding after an edit" in [Holding the `.MSN` as the document](#holding-the-msn-as-the-document)), which builds the object through `MissionScene.CreateObject`, the scene load's own path, its model built and uploaded then when nothing else in the mission draws with it; the ground is levelled under it as after a move, and it is selected. The add is one step of the undo history: Undo takes the records out again and rebuilds, and Redo puts the same ones back, under the same GUIDs, with the same object standing for them. An added structure and its group move as any other.
- **Changing sides.** A group's view offers Human or Cybrid as its Team, the group's side (block 11 `0x6e`), for every group but the player's squad; the side is the group's, so all its members change, and the view says how many when there are others. An object's view shows its group's team fixed, as controlled by the group. `SideChanger` writes row 16's side in the record of the group's GUID that supplies it and generates again, then sets the index's copy and each member's simulation object from the generated field, as one step of the undo history.
- **Deleting objects.** An object's view has a Delete button, and the Delete key deletes the selected object unless a text field has the keyboard or a drag is under way; either runs once the frame's panels are drawn. `ObjectDeleter` deletes through `RosterDeletion` (Core, `Data/File/Msn/RosterDeletion.cs`): every record of the object's GUID is removed from its roster row (12, 13 or 14), whatever its condition, and the GUID is cleared from every row-16 member slot naming it under the group's roster, in every record of the group's GUID. A group left with no member in any record loses all its row-16 records, and the view names the group that goes with the object. Nothing is renumbered by hand, as `.MSN` refs name GUIDs. The variant alternatives a deleted record drew from stay, and deleting a variant-keyed record moves every later draw ("Conditions and variants" below). The roster shrinks, so the slot caps count only what can spawn. A GUID with no record resolves to `-1` (`MissionGenerator.cs:473-496`), so the delete is refused while an objective, an action or an order names the object, or names the group the delete would remove, and while the object fires an action of its own when engaged or defeated, a variant alternative it can draw included; every record counts whatever its condition, and the view lists them as links. The player's squad is refused (group 0's view removes squadmates, "The player's squad" below), and so is anything in a plain `script.dat`, which opens read-only. The delete is one step of the undo history; the editor's state is built again from the generated file after it and after its undo and redo ("Rebuilding after an edit" below), and the ground is levelled again as after a move.
- **The player's squad.** Group 0's view shows the player's machine, then each squadmate: group 0's members in the unbroken run from its second slot, which the squad build reads (`Squad_SetPositionsInPlay`, [`../retail/shell/main-menu.md`](../retail/shell/main-menu.md#starting-a-practice-mission)), in that order. The player's own object's view shows the player's machine, and a squadmate's object's view that squadmate. First they say which Hercs the squad pilots in this mission, by the launch's own rule (`MissionSquad`, which `MissionFileLaunch.Open` and `OpenNew` hand out beside the document, from `ShellTrainingLaunch.PilotsMissionMachine`). The player pilots the mission's own group-0 machine on practice rows 0 to 3 and in every mission loaded as `INSTANT ACTION` (one `gam\career.dat` does not list, and a new mission), and a stock fit of the practice screen's Herc Type, option `0x28` as `DATA\prefs.cfg` holds it, on rows 4 to 7; on every one of those the squadmates pilot group 0's further machines, and the view says that the last squadmate listed stays behind and how many go (the retail bug in that doc's squad build, which this engine keeps). In a campaign mission the player and the squadmates pilot the career's squad from `DATA\player.mec`, and group 0's squadmates set only how many squad positions are in play ([`../retail/shell/campaign-loop.md`](../retail/shell/campaign-loop.md#loading-the-careers-mission)); the view says in bold that the HERCs and loadouts set here are not used there. Then each machine is edited in every `.MSN` mission: a chassis choice of the nine Herc Type steps through, and one row per mount the chassis has (`Herc_CapacityForType`), each offering the weapons of the weapons screen's list whose chassis layout (`gam\arm_*.dat`, `ShellArmingLayouts`) has a record for that socket, and for a missile rack or the Razor's launcher the four guidance kinds ([`../retail/shell/weapons-and-repair.md`](../retail/shell/weapons-and-repair.md#fitting-a-weapon)). The career's unlock flags and the armory's stock, which gate the weapons screen's list too, are not applied, as a mission's machine is fitted from no stock. A weapon chosen takes the guidance the weapons screen fits it with, ARH on a missile rack and none otherwise. A chassis chosen comes with its stock fit from `gam\ini_*.dat` ([`../retail/formats/herc-catalogs.md`](../retail/formats/herc-catalogs.md#gamini_dat--the-stock-fit-per-chassis)), an empty mount `0` and each slot past the capacity `-1` with the filler 5, as the retail squad records have them. `MachineFitter` writes each field that changes in the record supplying it, all of one edit's in one change; the player's machines of `TRAIN1` to `TRAIN4` and `TRAIN5`'s squad records are variant-keyed, so their edits take overlay records ("Conditions and variants" below). Group 0's view adds a squadmate after the last and removes any (`SquadEditor`, through `SquadRoster`, Core, `Data/File/Msn/SquadRoster.cs`). A new squadmate is a row-12 record appended with a new GUID, unconditioned and with no variant key, of the player's machine's chassis as it stands with that chassis's stock fit, every other field `TRAIN1.MSN`'s player record's as File > New mission writes it, named in group 0's member slot just past the run. A remove moves each later squadmate up a slot, so order matters and the view says so, and removes the squadmate's records as a delete does. An add is refused past three squadmates, the three squad members the player structure points at and the squad build fits ([`../retail/shell/squad-and-crew.md`](../retail/shell/squad-and-crew.md#the-rows)), and past DBSIM's 100 block-7 slots, which the squad's `player.mec` entries share, counted as the mission check counts them; a remove is refused as a delete is, while an objective, an action or an order names the squadmate or it fires an action of its own, and the view names them. Each edit is one step of the undo history, run once the frame's panels are drawn, and builds the editor's state again ("Rebuilding after an edit" below), which first builds the handoff's `player.mec` again as the launch would from the new generation: where the squad pilots the mission's machines, the scene's squad takes the new chassis, fits and squadmates, a squadmate left behind having no object, and File > Export copies that squad.
- **Saving.** File > Save (Ctrl+S) writes the mission's `.MSN` and its text, through `MissionFileTransformer` and `MissionStringFileTransformer`, as content-only loose files `MSN\<name>.MSN` and `MSN\<name>.ENG` under the install, the text taking the extension `Msn_LoadEngText` looks for in the shell's language (`.FRE`, `.GER`), as the open reads it (`SavedMissions`, `src/Herculan.Engine/Shell/SavedMissions.cs`). A loose file at a resource's path is read before any archive ([`../retail/formats/vol-archive.md`](../retail/formats/vol-archive.md#loose-files-on-disk-carry-no-prefix)), so this engine's shell and the editor load the saved mission for that name; whether VSHELL's mission load opens it through `VolRStream_Open` is that doc's Open item. A file being replaced is first copied to `<file>.bak`, one generation. The first save of an archive mission, which creates the override, asks first and says that deleting the loose files goes back to the archive's. File > Save As takes a name of up to eight letters, digits or `_`, upper-cased, asks before replacing another mission's saved files, and renames the mission: the window title, later saves and the browser follow. A name no archive holds opens as `MissionFileLaunch` opens any mission `gam\career.dat` does not list, as `INSTANT ACTION`. Before writing, either runs `ScriptDatLint` over the generated `script.dat` and, when it finds anything, gives the count and the first six findings and asks Save anyway or Cancel. The window title marks unsaved changes with `*`; the saved state is the undo history's depth and top step (`EditHistory`), so an undo back to it is clean. Before New mission or Load from VOL replaces the mission, before Back to game or Esc, and when the window is closed, the editor asks Save, Discard or Cancel; a window close is refused while it asks (`EngineWindow.CloseRequested`, which clears GLFW's close flag in its close callback). File > Export script.dat writes the generated `script.dat` and `mission.str`, with the squad's `player.mec` as last built and the `mission.var` the open wrote, into a folder typed in, and refuses the install's `DATA\` (`HandoffExport`). A plain `script.dat` has all three disabled, the menu saying why.
- **Objectives and timers.** An objective's view gives mandatory or failure, the subject (boxed in the scene), the condition, for condition 0 the route (highlighted) and the subject group's first order slot on it, the `mission.str` failure text and the counter writes. A timer's view gives the delay, the action that starts it and the actions it fires, and the action view links to it.

### Gaps in what is in place

- **Waypoint height.** A moved waypoint's point is written with Z 0, as 1487 of the 1488 retail waypoints have it. DBSIM reads a waypoint's Z as the starting altitude of a flight standing on its route's first waypoint, and the heads-down map projects the player's route icons with it ([`../retail/simulation/ai-goals.md`](../retail/simulation/ai-goals.md#the-route-cursor-is-loaded-once)); everything else works in the ground plane. A waypoint has no field or handle for it; only a flyer group standing on its route's first waypoint sets it, through the group's Z handle. This engine's heads-down map places route icons by X and Y alone.
- **Waypoint and group views.** The route view lists its waypoints' coordinates and the group view its point read-only, with no typed fields as an object's view has, and neither warns when a waypoint or a group is moved outside the mission box as opened, though that grows the box and the heads-down map's frame as an object does (the box overlay shows it).
- **Area tint.** Only a selected area is tinted. A selected action's areas are outlined, not tinted: `SceneRenderer.Highlight` holds one region. The tint is painted on the terrain alone, not on a structure's ground plane (its shadow and floor plates) inside the area.
- **Adding.** Only structures can be added, and an added structure's type is fixed once it is added. A herc, a flyer or a ground vehicle (which drives, and whose group needs orders the Toolbox has no way to set) cannot ([Per row](#per-row)).
- **The player's squad.** An overlay record cannot carry a field's unset value, so a field a variant supplies keeps the variant's value where an edit would unset it: after a chassis change on `TRAIN1` to `TRAIN4`, a slot past the new capacity keeps the variant's weapon and a mount that takes no guidance its ammunition type, neither of which the squad build or DBSIM reads. A launcher's mount whose stock fit carries the filler 5 is written SARH (0) instead, which DBSIM reads a 5 as ([`../retail/simulation/weapon-mounts.md`](../retail/simulation/weapon-mounts.md#the-join--mechloadout_constructweaponmounts-0040fff8)): the editor's choice, which leaves 0 in the generated record and the `player.mec` where the launch of an unedited stock fit holds 5. Removing a squadmate whose record draws a variant, as `TRAIN5`'s do, moves every later draw ("Conditions and variants" below).
- **Deleting.** Only roster objects are deleted, and a group only with its last member: nothing deletes a group, route, trigger area, action, timer or objective directly. A refused delete cannot be forced, and the view offers no way to clear the reference that refuses it.
- **Framing.** A double-click on a link in the Properties panel selects without framing. A timer stands nowhere and is not framed.
- **Top-down view.** It is the perspective camera at its pitch limit, 88 degrees down rather than 90, not an orthographic map: things stand up from the ground toward the edges of the view, and a point's place on screen shifts with its height. It frames the zone's grid as it opens, not whatever window size it is later resized to.
- **Ground planes from high up.** A structure's ground plane (shadow, floor plates) is ranked against the terrain by the cell `HeightGrid.PickDrawCell` files it under in the visible region, which `TerrainVisibleRegion.Update` keeps from the last view whenever the view's frustum, cut off at the zone's visibility range, reaches no ground, as it may from the top-down view's height. How the planes draw there has not been looked at.

Counts for the retail missions: 58 of 62 use trigger areas, 257 distinct areas named 143 times as boxes and 132 as circles, 16 shared by more than one action. Subjects are the player in 142 of 338 actions and the player's group in 170. `C2_01`'s boundary strips and `TRAIN8.MSN`'s three defeat-chained reinforcement waves ([`../retail/simulation/mission-deployment.md`](../retail/simulation/mission-deployment.md#train8msn-end-to-end)) are good test cases.

### Groups in the scene (blocks 10, 11)

Two things the group display still lacks. Ghosts of the formation slots a group leaves empty need the formation tables, which only `MissionLoader` holds. An order's own point (`+0x04`, set in 47 orders) is read only by the briefing map, and only off the squad's first order ([`../retail/simulation/ai-goals.md`](../retail/simulation/ai-goals.md#the-order-record)); mark it as a distinct briefing-only marker or leave it out.

Size: small each.

### Waiting groups as true ghosts

Outlining stands in for ghosting. Drawing the meshes translucent instead needs a tint or alpha path in `SceneRenderer`.

Size: small–medium.

### Action graph

The action view walks the wiring one link at a time; a node graph of the mission's actions, timers and the objects and groups between them would show it at once.

Size: medium–large.

### Left out

- **Drop-pod and on-foot arrival points.** Picked at run time relative to the player's position and heading when the action fires; nothing static to draw.
- **Detection and engagement ranges** (50,000 and 100,000 units). Simulation constants, not mission data; a per-object debug ring at most.
- **Variants and conditions.** The editor shows the mission as one generation of its `.MSN` resolves it ("Conditions and variants" in [Holding the `.MSN` as the document](#holding-the-msn-as-the-document)); which records a condition or a variant gates, it does not show ([The `.MSN` layer](#the-msn-layer)).

## Gaps on the write path

### 1. Positions are indirect

An object does not hold a position; it holds a `PositionRef` index into block 1. Most retail roster records carry `-1` there, so the object inherits its group's point plus a formation offset ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 2, gives the ones that name their own), and moving one gives it a point of its own. `MissionDocument.PlacePoint` appends a row-6 record with a new GUID, which the generation exports last in block 1, so nothing shifts, or rewrites the point in place once the moving field is all that names its GUID. It does not look for an identical existing point to reuse: file length is not a constraint.

Points are shared on purpose. In 45 of the 62 retail missions a route waypoint is the same block-1 point as a trigger area's center or corner (94 of the 886 distinct waypoint points, from `HercWorks.Query routes` and `actions`): that is how a mission fires an action when a waypoint is reached. `C1_01`'s player route runs through points 119, 121, 122, 123 and 124, its drop-pod triggers are circles about 121 to 124, and the groups those triggers bring in deploy on 119. So a waypoint drag moves the shared point, and the trigger and the groups move with it; giving the waypoint a point of its own, which Alt+drag does, leaves them where they were. A group drag (block 11) makes the same choice the same way, and moving an area corner (block 4) directly will meet it too.

### 2. Three consequences of appending

- **Block 1's extent frames the heads-down map** (see [`../retail/simulation/heads-down-display.md`](../retail/simulation/heads-down-display.md#the-maps-frame-of-reference), and `MissionBox`), and the mission box. A point outside the current box silently rescales the player's in-game map and moves the boundary warning and abort lines. The object view warns on it, and the mission box overlay is rebuilt after each edit.
- **File length is not a constraint.** `DBSim_LoadScriptDat` (`00424308`) reads through a `FileRStream` block by block and allocates each of blocks 1-6 and the group array from its own count, so a file longer than the retail 13,520 bytes reads correctly. Its fixed arrays are the per-roster slot flags and slot maps ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#the-two-pass-read--and-what-it-means-for-dbsim-keeps)); past them it writes over neighbouring globals. Appending block-1 points is unaffected; adding roster records is not: the mission check reports a roster past its cap, and the editor refuses to add a structure past block 9's. VSHELL's own reader, `ShellMap_LoadScriptDat` (`004243d7`), has not been checked for caps, and it reads a save slot's file for the briefing map.
- **A mech's or flyer's own point has never been observed live.** No retail mech or flyer record names one ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#placement--the-actual-rule), rule 2), so `Mech_AttachToGroup` and `Flyer_AttachToGroup` honouring it is RE-derived and engine-implemented, and the editor's moves of either rely on it. Structures' is exercised by retail data. Confirming it means writing such a file and running retail DBSIM.

### 3. Moved is not the same as stays there

- `MissionPlacement` carries `FormationOffset` even when the record supplies its own position, and AI followers hold formation on their leader every tick. For a non-leader group member the edit sets a spawn position the AI may walk out of; the object view says so.
- A group with no point of its own stands on its route's first waypoint, so moving that waypoint, as a plain group drag does, moves the start of the route too. Given a point of its own (Alt+drag), it spawns there instead, its route unchanged.
- A paints-ground base group snaps to a fixed spot in its tile, so a small move does nothing and a larger one jumps a whole tile ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#the-anchor)); the base pad overlay shows the tile.
- A group waiting to deploy by drop pod or on foot is placed at a placeholder, so moving it changes nothing once the mission runs ([`../retail/simulation/mission-deployment.md`](../retail/simulation/mission-deployment.md#arrival--group_deploymentcheck-004236c4)); its view says so. One arriving in place, and a held-back structure, stand where they are placed: the structure, solid and undrawn, from the first frame ([`../retail/simulation/mission-deployment.md`](../retail/simulation/mission-deployment.md#held-back-structures-stand-from-the-start)).

### 4. Live scene refresh

An object move re-places that object's items and pick sphere. After every change to block 1, `PointFollowers` places again, by the loader's rules, whatever stands on a point that moved: route points, trigger areas, each group's point and heading (its own point, else its route's first waypoint, facing along the first leg when it names no heading) with the members spread from it, a paints-ground group's pad outline, and objects whose roster record names the point. The positions it moves are editor copies in `MissionIndex`; `Mission` and the mission check stay as the mission was loaded or last rebuilt after an add or a delete (a `MissionPlacement.Position`, the orders' routes and the actions' areas go stale, and nothing in the editor reads a position from them). The ground is levelled and the pads painted again where the structures and pads now stand (`TerrainLeveller`).

## Authoring a mission from scratch

Everything in [In place](#in-place) starts a new mission, moves something, changes a group's side, adds or deletes an object, or edits the player's squad; every other field of every record is shown read-only or not at all. This is what building a mission from nothing needs beyond that.

### The `.MSN` layer

The editor holds a VOL mission as its `.MSN` and `.ENG` and shows it through the `script.dat` generated from them, the one VSHELL writes once it has filtered and resolved the `.MSN`. What the `.MSN` holds beyond that, the editor neither shows nor edits:

| `.MSN` part | What it carries |
|---|---|
| [Row 1](../retail/formats/msn-mission-file.md#the-conditions--row-1) | the campaign-flag comparisons and random draws every record's condition names |
| [Row 2](../retail/formats/msn-mission-file.md#the-header-patch--row-2) | the header words, patched by condition, and flags to clear |
| Row 3 | the briefing and debrief movie ids |
| Row 4 | the objective, briefing and intelligence lines and the briefing movie. `script.dat` keeps only the objective lines, as block 13, which the outliner lists read-only |
| [Row 5](../retail/formats/msn-mission-file.md#row-5--the-debrief) | the debrief lines and movie |
| [`.ENG`](../retail/formats/msn-mission-file.md#the-eng-string-table) | every line of the mission's text, with conditioned replacements. The editor reads the generated `mission.str` and edits none of it |
| [Variants](../retail/formats/msn-mission-file.md#variants) and [repeated GUIDs](../retail/formats/msn-mission-file.md#repeated-guids) | random alternatives and condition-dependent overrides, resolved before `script.dat` is written |
| GUIDs | how `.MSN` records name each other, where `script.dat` names by array position |

A mission the shell loads, practice or campaign, is an `.MSN`. A practice mission needs at least row 2's header and group 0's row-12 squad (`TRAIN1` and `TRAIN3` carry no row 4), and an objective's failure text needs the `.ENG`; a campaign mission uses rows 1, 3, 4 and 5 and variants too. File > New mission writes the practice set ([In place](#in-place), "New mission").

### Holding the `.MSN` as the document

The `.MSN` and its `.ENG` are the editor's document, `MissionDocument` (`Data/File/Msn/MissionDocument.cs`), with `script.dat` a view generated from them after each edit. Paths are under `src/HercWorks.Core/` unless named otherwise.

**The model.** `MissionFile` (`Data/File/Msn/MissionFile.cs`) holds all 17 rows, and `MissionFileTransformer` reads and writes them in file order (`Io/Transform/Common/MissionFileTransformer.cs:11-45`, `:312-340`). Rows 1, 3, 4 and 6 to 17 are typed records whose fields are settable properties (`:57-306`), every GUID-keyed one a `MapObject` with a settable `GUID` (`Data/File/Msn/MapObject.cs:7-10`). Row 2 is a raw `short[41]`, `MissionSettingsPatch.Data` (`Data/File/Msn/MissionSettingsPatch.cs:31-33`): its layout (a condition, ten header words, thirty flag indices) is what the generator reads (`Io/Transform/Common/MissionGenerator.cs:345-378`), but nothing names the words. Row 5 is raw bytes, `MissionFile.DebriefBytes` (`MissionFile.cs:33`, transformer `:27-28`): the debrief reload reads each 32-word record as a condition, thirty text refs and a row-3 ref (`MissionGenerator.cs:150-179`), and no type does. Inside the typed rows some spans stay unnamed words or arrays (`Unk04`, `Unk06`, `Unk1A`, row 12's and row 16's `DeadZone`, row 13's `FlagSpan`), and row 10's counter pairs are a flat `short[20]`. The `.ENG` is `MissionStringFile`, its entries settable (`Data/File/Msn/MissionStringFile.cs:44-72`), and its writer takes each length from the text (`Io/Transform/Common/MissionStringFileTransformer.cs:36-55`). `HercWorks.Query census` round-trips all 62 `.MSN` and all 62 `.ENG` files in `ZONES.VOL` byte for byte, `DEMO2.MSN`'s truncated row 17 included (a null in `MissionFile.Objectives`, `MissionFile.cs:68-78`). A row is a fixed array, so adding a record replaces the row's array. `MissionFile`'s lookups (`GetPoint`, `GetMech` and the rest, `MissionFile.cs:80-108`) ignore conditions and variants and merge no overlays, so they are not what a mission resolves to; only the generator gives that.

**Provenance.** `MissionGenerator.Load` takes the `.MSN` as bytes, not a `MissionFile` (`MissionGenerator.cs:103`), and walks them with its own cursor, so an edited `MissionFile` is written before it is generated from. Both read the rows in the same order, so the loop counter of each `Read…` method is the record's index in `MissionFile`'s row array, a record that fails its condition included. `MissionGenerator.Provenance`, a `MissionProvenance` (`Io/Transform/Common/MissionProvenance.cs`), is told by the generator as it adds, replaces, overlays and variant-copies, and answers which records supplied what it writes. `Slot(block, index)` gives an exported `script.dat` record's `SlotProvenance`: the `MsnRecordId` (row and index) that created the slot, the records merged into it in read order, each `VariantCopy` (the record that asked, the source it copied from and the words covered), and `Word(word)`, per `.MSN` word, a `WordSource` naming the record whose write the slot holds and, for a copied word, the variant source it was authored in. `ExportedSlot(record)` is the reverse, the `ScriptDatSlot` a record created or was merged into, null for a record that failed its condition, has GUID `-1` or is a variant source. `Lines` and `LineOf(engRecord)` do the same for `mission.str` lines: the `.ENG` record that placed each and the one whose text it holds. It covers blocks 1 to 12, block 13 as row 4's slot 0, and every `mission.str` line; row 2's header patches and row 3's values, which reach only the header and the row-4 and row-5 movie ids, are not traced, and a row-6 point with its sum flag set reports its coordinates as its own record's. Row 8's word 4 stands for its waypoint count and list together. It changes nothing the generator writes, which its reproduction of two retail TRAIN5 handoffs keeps checked.

**Conditions and variants.** Every record passes `Gate` (`:251-263`) against the row-1 survivors. Row 1's type 0 compares the caller's flag array (`:200-208`), type 1 draws from the caller's roll (`:210-215`) and type 2 tests its parent's draw (`:217-222`); `PickVariant` draws again for every record that asks, in file order (`:290-312`). Row 2 zeroes flags in the caller's array and writes into the caller's clear list (`:345-378`), so each generation needs fresh copies of both. The editor's VOL open goes through `MissionFileLaunch.Open` (`src/Herculan.Engine/Shell/MissionFileLaunch.cs`): a practice mission's flags are cleared and flags 3 to 6 seeded (`ShellTrainingLaunch.SeedDrawnFlags`), a campaign mission's start empty and take the career position's seed, and every draw comes from `ShellTrainingLaunch.StartupRandom`, seeded from the tick count (`src/Herculan.Engine/Shell/ShellTrainingLaunch.cs`), so opening the same mission twice can pick different variants. A practice load then overwrites header words 0 and 5 to 9 with the practice options (`ShellTrainingLaunch.PracticeHeader`), and a campaign load words 0, 5, 6 and 7 (`ShellCampaignLaunch.Write`). `HercWorks.Query lint` uses zero flags and a roll of 0 throughout (`src/HercWorks.Query/LintQuery.cs:22-23`).

A generation (`Data/File/Msn/MissionGeneration.cs`) takes the flags the load was handed, before its row 2 cleared any, a fresh clear list for each run, the header words the load wrote over, and draws from a copy of VSHELL's generator as it stood when the load began drawing, copied again for every run (`SimRandom.Copy`). Each generation therefore draws what the handoff's load drew, so the squad its `player.mec` was built for is the document's, and nothing in the scene reshuffles on an edit. No command picks a new seed, and no flag state can be chosen. Draws are made in file order, row 1's type-1 records first, then each variant-keyed record of rows 8, 12, 13 and 14 as it is read (the keys of rows 6, 7 and 15 are `-1` in every retail file). An edit that appends records with no variant key, as every add does, leaves every draw as it was; deleting a keyed record, or adding a draw ahead of others, moves the draws after it. A roll of 0 throughout is stable under every edit but shows one outcome only.

An edit writes the record that supplied the value in the editor's state:

| The `script.dat` value came from | The edit writes |
|---|---|
| a row-3, 6, 7, 8 or 9 GUID carried by more than one surviving record (replace) | the last surviving record of the GUID, whose payload the slot holds. 451 row-6 GUIDs in 24 missions are carried by two or more unconditioned records (`HercWorks.Query repeats`) |
| a row-10 to 16 GUID carried by more than one surviving record (overlay) | per field, the last surviving record of the GUID that sets it, else the first |
| a field of rows 12 to 15 copied from a variant | not the source, a GUID `-1` alternative shared by every record that can draw it, but a record of the same GUID appended to the row, carrying that field alone, under the condition of the record that drew the variant, so it overlays the field whatever is drawn in every state that record survives in. An unconditioned one would create the slot alone, every other field unset, in a state where every other record of the GUID fails. `MissionDocument.SetField` writes one for rows 12 to 14 |
| a row-8 waypoint list copied from a variant (2% of retail routes) | the alternative, moving every route that draws it (`MissionDocument.SetWaypoint`). Detaching the route instead, its key set to `-1` and its own list written, would take a draw away and move every later one. Row 8 replaces rather than overlays, so an appended record cannot carry one waypoint |
| a field set to its unset value (a member slot to `-1`) | every record of the GUID that sets the field, whatever its condition: an overlay cannot carry an unset value |

A supplier with a condition holds the edit only in the states it survives in, which no view says yet. Counting what shares a point counts every record naming its GUID, whatever its condition, since one conditioned out in the editor's state names it in another.

**The tools.**

| Tool | What it writes in the `.MSN` |
|---|---|
| `MissionDocument.CountPointRefs` and `PlacePoint` (Core) | count the records of rows 8, 9 and 12 to 17 naming a row-6 GUID, whatever their condition; place a point by rewriting the GUID's record when the moving fields are all that name it and the GUID has one record, else by appending a row-6 record with a new GUID. Row 6's variant key and sum flag are unused in every retail file ([`../retail/formats/msn-mission-file.md`](../retail/formats/msn-mission-file.md#row-6-field-decode--the-point-record-dat_0047064e-22-bytesrecord)), so a point's coordinates are always a row-6 record's own; `SetPoint` refuses one that is not. `ScriptPointRefs` counts a plain `script.dat`'s refs for the views and places a drag's preview in the generated file |
| `PointMover` | the supplying row-6 record's X, Y and Z (`SetPoint`), and the GUID in row 12, 13 or 14's `PositionRef`, row 16's `PositionRef` (`SetField`) or row 8's `Waypoints` (`SetWaypoint`). A variant-keyed mech, flyer or structure (48%, 30% and 0.4% of rows 12, 13 and 14) has its own `PositionRef` overwritten by the variant's (`MissionGenerator.cs:810-818`, `:851-854`, `:882-885`), so its move takes the appended overlay record, and never rewrites the point in place, which every record drawing the variant shares. A record with a new GUID is exported last in its block; the editor's state is rebuilt from the generated file, which builds the scene object. A join appends the record and point and writes the member slot in the group's supplying record, the first slot no record of the group's GUID fills in any state |
| `ObjectDeleter`, through `RosterDeletion` (Core) | removes every record of the object's GUID from its roster row (`MissionDocument.Remove`) and clears the GUID from every row-16 member slot naming it under the group's roster, in every record of the group's GUID (`MissionDocument.ClearMember`); a group left with no member in any record is removed too, all as one `Change`. Refused by `RosterDeletion.Check` for the player's squad, and while an objective, action or order names the object or the group it would remove, or the object fires an action of its own ("Deleting objects" in [In place](#in-place)) |
| `SideChanger` | row 16's `Side` in the record supplying it (an overlay field whose unset value is `-1`, `MissionGenerator.cs:966`) |
| `MachineFitter` | row 12's `TypeIndex`, and `WeaponRefs` and `WeaponSecondary` per slot (overlay fields whose unset values are `-1`, `-1` and 5, `MissionGenerator.cs:822-824`), in the record supplying each (`SetField`), for the herc a group-0 member slot names; a field a variant supplies that an edit would unset is left, or for a launcher's guidance written SARH (0) ([Gaps in what is in place](#gaps-in-what-is-in-place)) |
| `SquadEditor`, through `SquadRoster` (Core) | an add appends a row-12 record (`Append`) and names it in group 0's member slot just past the squadmates' run, in the record supplying that slot (`SetField`); a remove writes each later squadmate's GUID into the slot before it (`SetField`), unsets the run's last slot in every record of the group, and takes the squadmate's records as `RosterDeletion` does, all as one `Change`. **Regenerating on each edit.** Each `MissionDocument` edit writes the `MissionFile`, keeping copies of the rows it changed for undo (`MsnEdit`), then writes the file, generates from it, parses the output as a `ScriptDat` and copies its header and blocks into `MissionDocument.Script`, the one `ScriptDat` everything reading the document holds (`PointFollowers`, the tools' own checks). Edits made inside one `MissionDocument.Change` come back as one `MsnEdit`, and are all put back when one of them fails. Undo and Redo write a step's rows back and generate again. Writing, generating and parsing touch arrays of a few hundred records; the scene's terrain and models are not reloaded. A move and a side change keep every generated record where it was, so the incremental scene updates apply as they are. A Save writes the `.MSN` and the `.ENG` as they stand, and an export writes the generated `script.dat` and `mission.str`; neither builds anything.

**Rebuilding after an edit.** A delete moves every later generated record of its block down one, an add's records are exported last, and a squad edit changes the squad the launch builds, so after any of them, and after the undo or redo of any, `MissionRebuild` (`src/Herculan.Engine.Editor/MissionRebuild.cs`) builds the editor's state again from the generated file. For a mission loaded in training mode it first writes the handoff's `player.mec` again, as the launch would write it for the generation (`MissionSquad.PlayerMec`: `ShellTrainingLaunch.NewCareer` drawing again from VSHELL's generator as it stood when the open began, `ShellTrainingLaunch.BuildSquad`, the training load's squad half, over the document's `MissionDocument.Generator`, and the export); a campaign mission's squad is the career's and stays. Then it builds a `Mission` (`MissionLoader.Load(content, script, path)`), `MissionIndex`, the pick spheres, the overlays' lines, `PointFollowers` and the mission check, which therefore runs again then and only then. Each placement stands on the scene object already built for the `.MSN` record that created its slot, matched by GUID through provenance, by type and by weapon fit, since a mech's loadout is built with its object, and the player's squad by its order in `player.mec`; its `SceneObject.Placement` is pointed at the new indices. A placement with none gets a new object from `MissionScene.CreateObject`, and an object no placement names leaves the drawing. No object is discarded, so an undone delete stands the same object, model and drawing where it stood, and terrain and models are not loaded again. The selection survives when what it names does: an object by identity, or else as the object now standing for the same record, which a chassis change builds; a group by its GUID; and is cleared otherwise. A step of the undo history that holds block indices, a move's object or a side change's group, needs no rewriting: the history is undone last first, so a step only ever runs against the `.MSN` it was made on, whose generation gives the same indices, and every step that adds or removes records rebuilds as it is undone or redone.

**A plain `script.dat`.** The editor edits `.MSN` missions only. `DATA\script.dat` and a save slot's `sav\script%d.dat` have no `.MSN` beside them, and none can be regenerated reliably from one: `DATA\script.dat` does not record its mission, and a regeneration's campaign flags and draws need not be the ones it was written under. The editor opens such a file read-only, for inspection: every edit tool refuses with a reason its view shows (`PointMover.WhyReadOnly`), the Toolbox adds nothing and says why, Undo and Redo stay empty, and Save, Save As and Export are disabled with the same reason.

Checked and not found:

- No `HercWorks.Query` report counts the row-10 to 16 GUIDs carried by more than one record; `repeats` covers rows 3 and 6 to 9. How often an overlay edit meets a conditioned supplier in retail is not counted.
- Whether every retail variant table has a child whose range holds a draw of 0 was not checked. A table with none makes `PickVariant` answer `-1` (`MissionGenerator.cs:306-311`), and a row-12 to 15 record that asked keeps its own refs unresolved (`:805-818`), which matters for a roll of 0.
- How long one write, generation and parse takes was not measured.
- The slot caps are checked against the file generated in the editor's state; no check covers the most records any flag state lets survive.

### Mission level

- **The header** ([`../retail/formats/script-dat.md`](../retail/formats/script-dat.md#header-format)) is not editable: File > New mission sets the theater, zone and day or night variant once, and nothing changes them, the objective type (offset 6, which picks the player's objective arm) or the training mission number after. The difficulty and the two training cheats are overwritten at every shell load, and a practice load writes the theater and the variant over the patch's too.

  The theater (offset 0, which picks `wld\world<theater * 2 + variant>`: the terrain texture bank, the palette, the sky and the fog) and the day or night variant (offset 18) are to be chosen in the New mission dialog and editable at any time after, shown live, the scene's world reloaded for the choice ([`../retail/formats/wld-world.md`](../retail/formats/wld-world.md)). Every retail load writes over the theater, a campaign's from its stage and a practice or `INSTANT ACTION` one as 1, and a practice or `INSTANT ACTION` load writes the practice screen's time of day over the variant; only a campaign mission plays its `.MSN`'s own day or night. A campaign mission already opens in the editor as the game plays it, on its stage's theater by its own day or night. Any other mission is to show its own choice, and the planned menu for playing user-made missions honours the `.MSN`'s theater and variant: this engine's departure from `INSTANT ACTION`, which the user chose. The New mission dialog's note that the game plays a new mission on theater 1 by the practice screen's time of day changes with it, and its zone list drops the theaters each zone's retail missions are played on, which only a theater choice needed.
- **The mission list.** File > Load from VOL lists each mission by its file name and whether it is saved or new; it is to show each one's zone and theater as well.

### Counters and caps

- **Mission counters.** Actions, objectives and out-of-action reports write counters, which persist into the campaign flags the next mission's row 1 tests ([`../retail/shell/campaign-loop.md`](../retail/shell/campaign-loop.md#the-campaign-flag-array-is-the-msn-condition-store)). Nothing lists which counters a mission writes, so nothing helps choose a free one or wire it to a condition.
- **Slot caps.** Adding mechs and flyers needs the refusal structure adds have, against `ScriptDatLint`'s 100 mech and 50 flyer slots.

## Suggested sequencing

What a new mission needs to become a mission, in order:

1. **Next:** the header fields, with the theater and day or night editable at any time and the scene's world reloaded live ([Mission level](#mission-level)).
2. Hercs, then flyers, added in groups with a first order (verb, route, subject), with route creation and editing.
3. Objectives with their text: the objective list, failure text and briefing.
4. Trigger areas, their corner moves through the same point placement included, actions and timers.
5. The campaign layer (conditions, variants, debrief) last.
