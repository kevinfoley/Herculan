# Handoff — the editor's `.MSN` document

How the editor holds a mission as its `.MSN` and `.ENG`, which record each edit writes, when it generates a `script.dat`, and how the editor's state is rebuilt after an edit. Part of the [editor handoff](handoff-editor.md). Paths are under `src/HercWorks.Core/` unless named otherwise.

## Building blocks

- `Mission` carries `Actions` (each `MissionAction` with its resolved `MissionTriggerArea` list), `ActionTimers`, `GroupOrders` (each order's `Route` resolved to points), `PlayerRoute`, `Objectives`, `GroupDeploymentActions`, `GroupKinds`, `GroupSides`, `GroupOutOfActionReports`, `GroupSetups`, `Coordinates` and `Text`. Each `MissionPlacement` carries its `Kind`, `GroupIndex`, `SlotIndex`, `EngagementActionRef`, `DefeatActionRef`, `StartingCondition` and `OutOfActionReport`; `Kind` and `SlotIndex` address a block-7/8/9 record and `GroupIndex` a block-11 one, which the game's load binds by.
- `MissionLoader.Load(content, script, path)` loads from a parsed `ScriptDat`, placing through `MissionPlacementRules`, which honours a roster record's own position over its group's spread, as `Mech_AttachToGroup` (`00417aa8`) does.
- `MissionGenerator` builds a `script.dat` from an `.MSN` as VSHELL does; `MissionFileTransformer` and `MissionStringFileTransformer` round-trip `.MSN` and `.ENG` files; `ScriptDatTransformer.Write` writes all 13 `script.dat` blocks.
- `HercWorks.Query actions|orders|objectives` cross-checks anything the editor shows; `records <MISSION> [--row N]` and `header <MISSION>` dump one mission's raw records, and row 2 beside the header it generates.
- `TrainingLaunchTests.ReproducesTheRetailTrainingHandoff` checks the generator's `script.dat`, `mission.str` and `player.mec` for a `TRAIN5` launch against a retail handoff byte for byte; `TrainingLaunchTests.LoadsEveryRetailMission` generates a `script.dat` from each of the 62 `.MSN` files and checks `ScriptDatTransformer` rewrites it byte-exact, not that the generation is unchanged; `ScriptDatRoundTripTests` rewrites the install's `DATA\script.dat` and every `sav\script%d.dat` as a prefix of the file read (they keep stale tails past block 13). Both skip without an install.

## The `.MSN` layer

The editor shows, selects, checks and edits a mission from its `.MSN` ([The layout](#the-layout)). A `script.dat` is what VSHELL writes once it has filtered and resolved the `.MSN`, and the editor generates one only for the open and for Export ([The generation](#the-generation)). What the `.MSN` holds beyond `script.dat`:

| `.MSN` part | What it carries, and what the editor does with it |
|---|---|
| [Row 1](../retail/formats/msn-mission-file.md#the-conditions--row-1) | the campaign-flag comparisons and random draws every record's condition names. Edited: flag tests, draws, ranges over a draw, variant tables and their alternatives ([conditions](handoff-editor-conditions.md)); a range over a table is shown read-only |
| [Row 2](../retail/formats/msn-mission-file.md#the-header-patch--row-2) | the header words, patched by condition, and flags to clear. Edited: the theater and the time of day |
| Row 3 | the briefing and debrief movie ids. Not shown |
| Row 4 | the objective, briefing and intelligence lines and the briefing movie; `script.dat` keeps only the objective lines, as block 13. Edited: the three lists of the record block 13 is written from, not its movie |
| [Row 5](../retail/formats/msn-mission-file.md#row-5--the-debrief) | the debrief lines and movie. Not shown |
| [`.ENG`](../retail/formats/msn-mission-file.md#the-eng-string-table) | every line of the mission's text, with conditioned replacements. Edited: the lines rows 4 and 17 reference; a trigger's leftover line is shown read-only and the debrief's not at all |
| [Variants](../retail/formats/msn-mission-file.md#variants) and [repeated GUIDs](../retail/formats/msn-mission-file.md#repeated-guids) | random alternatives and condition-dependent overrides, resolved before `script.dat` is written |
| GUIDs | how `.MSN` records name each other, where `script.dat` names by array position |

A practice mission needs at least row 2's header and group 0's row-12 squad (`TRAIN1` and `TRAIN3` carry no row 4), and an objective's failure text needs the `.ENG`; a campaign mission uses rows 1, 3, 4 and 5 and variants too. File > New mission writes the practice set.

## Holding the `.MSN` as the document

The `.MSN` and its `.ENG` are the editor's document, `MissionDocument` (`Data/File/Msn/MissionDocument.cs`), which `EditorMission.Source` holds. Everything the editor displays, selects and checks reads the document's layout, never a generated `script.dat` (the user's choice): a view built on the generation could not show a record it drops, and would hold block indices an edit renumbers.

### The model

`MissionFile` (`Data/File/Msn/MissionFile.cs`) holds all 17 rows, and `MissionFileTransformer` reads and writes them in file order (`Io/Transform/Common/MissionFileTransformer.cs:11-45`, `:312-340`). Rows 1, 3, 4 and 6 to 17 are typed records with settable properties (`:57-306`), each GUID-keyed one a `MapObject` with a settable `GUID` (`Data/File/Msn/MapObject.cs:7-10`). Row 2 is a raw `short[41]`, `MissionSettingsPatch.Data` (`Data/File/Msn/MissionSettingsPatch.cs:31-33`): a condition, ten header words and thirty flag indices, as the generator reads it (`Io/Transform/Common/MissionGenerator.cs:345-378`), with no word named. Row 5 is raw bytes, `MissionFile.DebriefBytes` (`MissionFile.cs:33`, transformer `:27-28`): the generator reads each 32-word record as a condition, thirty text refs and a row-3 ref (`MissionGenerator.cs:150-179`), and no type does. Unnamed spans remain inside the typed rows (`Unk04`, `Unk06`, `Unk1A`, rows 12 and 16's `DeadZone`, row 13's `FlagSpan`), and row 10's counter pairs are a flat `short[20]`. The `.ENG` is `MissionStringFile`, its entries settable (`Data/File/Msn/MissionStringFile.cs:44-72`), its writer taking each length from the text (`Io/Transform/Common/MissionStringFileTransformer.cs:36-55`). `HercWorks.Query census` round-trips all 62 `.MSN` and 62 `.ENG` files in `ZONES.VOL` byte for byte, `DEMO2.MSN`'s truncated row 17 included (a null in `MissionFile.Objectives`, `MissionFile.cs:68-78`). A row is a fixed array, so adding a record replaces the row's array. `MissionFile`'s lookups (`GetPoint`, `GetMech`, `MissionFile.cs:80-108`) ignore conditions and variants and merge no overlays; the layout merges a GUID's records ([The layout](#the-layout)), and only the generator gives what one load resolves to.

### The layout

`MissionDocument.Layout`, a `MissionLayout` (`Data/File/Msn/MissionLayout.cs`), is a read-only view of the `MissionFile` and its `.ENG` with every record present, built in one pass after every edit, undo and redo (the files are a few thousand records). It is what everything that displays or checks a mission reads, and what an edit consults to choose the record it writes.

- **One entry per thing a designer sees**, keyed as the `.MSN` keys it: points, headings, routes, trigger areas, actions, timers, hercs, flyers, structures and ground vehicles, orders and groups by row and GUID (`LayoutEntry`); row 2's header patches as one header (`LayoutHeader`); objectives by row-17 index; conditions by row-1 GUID; text lines by `.ENG` id (`LayoutLine`). Refs stay GUIDs, resolved to entries, never to indices.
- **The base.** A thing is shown by its base, the records of its key carrying the same condition as its first record (the one that creates it), merged in file order with the game's overlay-or-replace rule per row and its unset values (the user's choice). Each record under any other condition is a variation (`LayoutVariation`, `LayoutTextVariation`, `LayoutHeaderVariation`). The merge spans, unset values and variant copies are one table, `MergeRules`, which `MissionGenerator` merges by too, so the two cannot drift.
- **The first option.** A record with a variant key carries the first option of its table in row-1 order (`LayoutDraw`), the same every time (the user's choice); its entry lists every option.
- **Each field's supplier** (`LayoutEntry.Supplier`): the record whose value is shown, which is the record an edit writes ([Which record an edit writes](#which-record-an-edit-writes)).
- **Presence** (`LayoutPresence`): always, or the conditions it needs, composed from the record's own condition and, for a group member, its group's, and the variant tables it draws from.
- **No generation**: no condition is tested, nothing is drawn, nothing is renumbered.

`MissionDocument.LaunchHeader` is the ten header words the launch plays: the layout's header words with every word the open's launch writes over a loaded header written over them (`MissionGeneration.WriteHeader`); no condition is tested, so a row-2 variation is not applied.

### Provenance

`MissionGenerator.Load` takes the `.MSN` as bytes (`MissionGenerator.cs:103`), which `MissionDocument` writes from the edited `MissionFile` with each edit. Both read the rows in the same order, so each `Read…` method's loop counter is the record's index in `MissionFile`'s row array, a record that fails its condition included. `MissionGenerator.Provenance`, a `MissionProvenance` (`Io/Transform/Common/MissionProvenance.cs`), records as the generator adds, replaces, overlays and variant-copies:

- `Slot(block, index)` gives an exported record's `SlotProvenance`: the `MsnRecordId` (row and index) that created the slot, the records merged into it in read order, each `VariantCopy` (the record that asked, the source and the words covered), and `Word(word)`, a `WordSource` naming the record whose write the slot holds and, for a copied word, the variant source.
- `ExportedSlot(record)` is the reverse; null for a record that failed its condition, has GUID `-1` or is a variant source.
- `Lines` and `LineOf(engRecord)` do the same for `mission.str` lines: the `.ENG` record that placed each line and the one whose text it holds.
- `HeaderPatches` lists the row-2 records whose condition passed, and `HeaderWord(word)` names the one whose write a header word holds.

It covers blocks 1 to 12, block 13 as row 4's slot 0, the header and every `mission.str` line. Row 3's values (the row-4 and row-5 movie ids) are not traced, and a row-6 point with its sum flag set reports its coordinates as its own record's. Row 8's word 4 stands for the waypoint count and list together. Its reproduction of two retail `TRAIN5` handoffs checks that it changes nothing the generator writes.

Nothing in the editor reads it. `MissionDocument.Provenance` generates first, as the generation's other members do ([The generation](#the-generation)), and serves the tests that check a generation record by record: `MissionProvenanceTests`, `MissionFileLaunchTests` (which row-2 record supplies a header word), `ObjectiveEditingTests` and `SyntheticMsn`'s lookups of a GUID's exported slot.

### Conditions and variants

Every record passes `Gate` against the row-1 survivors. Row 1's type 0 compares the caller's flag array, type 1 draws from the caller's roll and type 2 tests its parent's draw (`ReadConditions`); `PickVariant` draws again for every record that asks, in file order, and `MissionGenerator.VariantPicks` gives each pick's table, range and source record. Row 2 zeroes flags in the caller's array and writes the caller's clear list (`ReadHeaderPatches`), so each generation needs fresh copies of both.

The editor opens a VOL mission through `MissionFileLaunch.Open` (`src/Herculan.Engine/Shell/MissionFileLaunch.cs`): a practice mission's flags are cleared and flags 3 to 6 seeded (`ShellTrainingLaunch.SeedDrawnFlags`), a campaign mission's start empty and take the career position's seed, and every draw comes from the generator the caller hands it. The editor's open hands `SimRandom.Lowest`, whose every step is 0, so every open of a mission draws the same ([What the editor shows](handoff-editor-conditions.md#what-the-editor-shows)); the game's load hands `ShellTrainingLaunch.StartupRandom`, seeded from the tick count. A practice load then writes header words 0 and 5 to 9 with theater 1 and the practice options (`ShellTrainingLaunch.PracticeHeader`), a campaign load words 0, 5, 6 and 7 (`ShellCampaignLaunch.Write`); the editor's generation of a practice load leaves words 0 and 9 to row 2 (`MissionOpener`, `MissionGeneration.WithoutOverwrite`). `HercWorks.Query lint --generated` uses zero flags and a roll of 0 (`src/HercWorks.Query/LintQuery.cs:28-29`).

A generation (`Data/File/Msn/MissionGeneration.cs`) holds the flags the load was handed before row 2 cleared any, a fresh clear list per run, the header words the load wrote over, and a copy of VSHELL's generator as it stood when the load began drawing (copied again per run, `SimRandom.Copy`). The document keeps the open's generation for its life, so each generation draws what the open's load drew, the squad its `player.mec` was built for is the document's, and nothing reshuffles on an edit.

Draws are made in file order: row 1's type-1 records first, then each variant-keyed record of rows 8, 12, 13 and 14 as it is read (rows 6, 7 and 15 carry key `-1` in every retail file). What moves the draws after it:

- moves them: deleting a keyed record or changing which versions of the mission it is present in; giving a record a table or taking it away; adding or deleting a row-1 draw, or changing whether one is made.
- moves none: appending records with no variant key (every add); a table's chances, its bound, adding or removing an alternative (a draw below any bound of 1 or more is one step of the generator). A new draw goes last in row 1, still ahead of every variant pick.

An open's draws, all 0, are moved by no edit, since each is 0 whatever is drawn before it; the list applies to the game's own loads, which draw at random.

### Which record an edit writes

An edit writes the record `MissionDocument.Layout`, a `MissionLayout` built again after every edit, undo and redo, names as the field's supplier, whether or not the generation keeps it. A thing's **base** is the records of its key carrying its first record's condition, merged in file order; each record under any other condition is a variation ([The layout](#the-layout)). The tools read the values an edit starts from (a slot list, an area list, a fit, a type) from the same base.

| The value | The edit writes |
|---|---|
| a field of a row-6, 7, 8 or 9 GUID (replace) | the GUID's last base record (`LayoutEntry.Supplier`; `MissionDocument.SetPoint`, `SetArea`). 451 row-6 GUIDs in 24 missions are carried by two or more unconditioned records (`HercWorks.Query repeats`) |
| a field of a row-10 to 16 GUID (overlay) | the last base record of the GUID that sets it, else the GUID's first record (`LayoutEntry.Supplier`; `MissionDocument.SetField`). Across the retail missions two or more records carry 1 row-11, 93 row-12, 3 row-13, 564 row-14, 4 row-15 and 124 row-16 GUIDs and no row-10 one; the records of 7 herc, 562 structure, 4 order and 11 group GUIDs among them carry different conditions (`HercWorks.Query repeats`) |
| a field of rows 12 to 15 the supplier copies from a variant (the layout shows each keyed record's first option) | a record of the same GUID under the supplier's condition, the base's, so it overlays the field whatever is drawn wherever the base is present (`MissionDocument.SetField`, rows 12 to 14): the GUID's last record when it comes after the supplier, carries the base's condition and draws no variant, so the fields of one edit (a chassis and its mounts) and of later ones share it; else one appended to the row carrying that field alone. Not the GUID `-1` alternative, which every record that can draw it shares; and not unconditioned, which would create the slot alone, every other field unset, in a state where every other record of the GUID fails. `MissionDocument.SetAlternativeField` writes the alternative itself instead (`VariantEditing.SetDrawnField`; `RosterFit.Write` for a type or fit unless the view's "Only this" is ticked), changing every record that draws it, and can write an unset value |
| a row-8 waypoint list copied from a variant (2% of retail routes) | the alternative, changing every route that draws it (`MissionDocument.SetWaypoint`, `SetWaypoints`). Detaching the route (key `-1`, its own list) would take a draw away and move every later one; row 8 replaces rather than overlays, so an appended record cannot carry one waypoint |
| a row-15 order another group slot names too (7 of the 609 order GUIDs the retail groups name) | a copy of every record of the GUID under a new GUID, named in the edited slot, and the field in the copy (`GroupOrders`) |
| a field set to its unset value (a member slot to `-1`) | every record of the GUID that sets the field, whatever its condition: an overlay cannot carry an unset value. A starting condition set to 100 is the exception: unset in the base's records only, so a record under another condition keeps the value it states (`StartingConditions.Set`) |
| a word the generation neither exports nor merges (row 10's pair count `0x1A`) | every record of the GUID, each set from its own pairs (`MissionDocument.RewriteEvery`) |
| a row-4 or row-17 record, which has no GUID and is named by nothing | the record itself, whatever its condition (`MissionDocument.Rewrite`); row 4's line lists are its first record's (`MissionTextEditing.PackageRecord`) |
| a line of text | the last base `.ENG` record of its id, those carrying the id's first record's condition (`LayoutLine.Supplier`, `MissionDocument.SetText`) |
| a `.ENG` id another text field references too | a copy of every record of the id under a new id (a failure text's three ids as one block), named in the edited field, and the text in the copy (`MissionTextEditing`) |
| a header word, which row 2's records patch into one header | the last base row-2 record that sets it, those carrying the first row-2 record's condition, else the first row-2 record, else a row-2 record appended unconditioned; its unset value (theater 1, day) in every row-2 record that sets it (`LayoutHeader.Supplier`, `MissionDocument.SetHeaderWord`) |

Where a variation's condition holds, a field it sets keeps the variation's value, so an edit of that field does not show in that version; the views of roster objects, groups and orders say so ([Present when](handoff-editor-conditions.md#present-when)). The scene and every view show the base, so such an edit shows in the editor whatever the variation sets. Counting what shares a point counts every record naming its GUID, whatever its condition.

### The tools

Each tool's edits go through one `MissionDocument.Change`, which comes back as one `MsnEdit` and is put back whole when any part fails. Every record a tool appends is unconditioned, has no variant key and takes a new GUID, the row's largest plus one (GUIDs are per row, `MissionFile.cs:102-108`), unless the row says otherwise; a record with a new GUID is exported last in its block.

### The generation

An edit, undo or redo writes the `MissionFile` or the `.ENG` in memory, keeping copies of the rows and `.ENG` records it changed for undo (`MsnEdit`), and builds `MissionDocument.Layout` and `LaunchHeader` again (`MissionDocument.Rebuild`). It writes nothing to disk and generates nothing. A theater or time-of-day change also builds the models and terrain mesh again ([Theater and time of day](handoff-editor-viewing.md#theater-and-time-of-day)); nothing else reloads terrain or models.

The generation, the `script.dat`, `mission.str`, provenance and generator run VSHELL's load gives (`MissionDocument.Script`, `ScriptBytes`, `MissionText`, `Provenance`, `Generator`), is made from the document's `MissionGeneration` when one of them is first read after an edit, and kept until the next. Two things in the editor read it:

| Reader | Reads | For |
|---|---|---|
| the open (`EditorMission.Open`) | `ScriptBytes`, `MissionText`, `Script` | writes the generated `script.dat` and `mission.str` over the handoff's and runs the game's load over them once (`MissionLoader.Load`), for the world alone: zone, theater, time of day, models and terrain (`MissionScene.LoadWorld`) ([Opening a mission](handoff-editor-viewing.md#opening-a-mission)) |
| File > Export (`MissionSaving`, `HandoffExport`) | `ScriptBytes`, `MissionText`, `Generator` | the exported `script.dat` and `mission.str`, and for a mission loaded in training mode its `player.mec`, built from the generation as the launch builds it (`MissionSquad.PlayerMec`: `ShellTrainingLaunch.NewCareer` drawing again from VSHELL's generator as it stood when the open began, then `ShellTrainingLaunch.BuildSquad` over the generator run). A campaign mission's squad is the career's, so Export copies the handoff's `player.mec` |

A generation that fails throws when it is read, so an edit is never refused for one; a failure shows at Export, as its reason under the folder field.

### Rebuilding after an edit

Every edit, a move and a side change included, and the undo and redo of each, can change where things stand: a move or a side change rewrites a group's or an object's fields, an add appends records and a delete removes them, a squad edit changes group 0's members, a type or fit change needs a new object, and a random-choice edit can change the option a record shows. After each, `SceneSync` (`src/Herculan.Engine.Editor/SceneSync.cs`) syncs the editor's state with the document; a theater or time-of-day change first dresses the scene in the new world ([Theater and time of day](handoff-editor-viewing.md#theater-and-time-of-day)).

1. The scene comes from the layout. `LayoutPlacement` places every group and roster record of `MissionDocument.Layout`, and every route, trigger area and action (`LayoutFeatures`), through the game's own placement rules over the values the layout resolves, keyed by GUID. `MissionPlacementRules` (`src/Herculan.Engine/World/MissionPlacementRules.cs`) is that code, which `MissionLoader` calls with what it resolves from a `script.dat`, keyed by roster slot: a group's point (its own, else its slot-0 order's route's first waypoint, else the origin), its heading (its own, else the route's bearing) and the paints-ground snap (`GroupSetup`); the first group in file order to name a roster record places it, at its raw slot index, and group 0 claims nothing (`ClaimMembers`); each member's place by formation slot, a roster record's own point and heading winning (`PlaceHerc`, `PlaceFlyer`, `PlaceStructure`); the squad's spread from group 0 (`PlaceSquadMember`); a pad's layout and lead member (`PadLayout`, `PadLead`). The placement is shared with the game, and the layout reproduces the generator only in the per-row merge and the option a keyed record copies (the user's choice); condition gating, compaction and renumbering are not copied. Each claimed record stands by its base's fields, a keyed record's carrying its shown option's point, heading, type and fit; variations are not placed. With conditions untested, two groups of different conditions can name one record: the first in file order places it, as the game does whenever both are present. The squad is one object per herc group 0's member slots reference, spread from group 0 at the slot's position, which is the entry the training squad build gives it (the user's choice, [The player's squad](handoff-editor-roster.md#the-players-squad)); a record group 0 and a later group both reference is the squad's alone.
2. Each placed record stands on the scene object already built for it, by its row and GUID, of its type and weapon fit (a mech's loadout is built with its object), where the spawn pass and the editor's draw put it; a record with none gets a new object from `MissionScene.CreateObject`; the object of a record no group places leaves the drawing but is kept, so an undone delete stands the same object again. Each object's `SceneObject.Placement` takes its type, fit, position, heading, side and formation slot from the layout; its roster slot and group index are `-1`, and the actions and out-of-action writes the game's load binds are unset, since the editor binds and ticks nothing (`SceneSync.PlacementOf`).
3. It builds `MissionIndex`, the objects, groups, routes and areas by GUID, which the outliner lists with the layout; the pick spheres and the overlay lines; and the mission check over the layout ([Mission check](handoff-editor-viewing.md#mission-check)).
4. The selection names a `.MSN` record, not a block index, so nothing is mapped: it is kept while the `.MSN` has its record (`EditorSelection.InFile`: a record of its row carrying its GUID, or for an objective a row-17 record at its index), an object while the scene has an object for its row and GUID, so the new object a type or fit change builds stays selected, a route's waypoint while the layout's route still has one there, and is cleared otherwise; an objective delete clears a selection of the deleted record, as the next record takes its index.

A drag's preview (`SceneSync.Preview`) places the same records again with the drag's overrides and builds nothing ([Moving](handoff-editor-placement.md#moving)). No undo step holds a block index: each holds the `.MSN` rows it changed.

## Saving and export

- **Save** (File > Save, Ctrl+S) writes the `.MSN` and its text, through `MissionFileTransformer` and `MissionStringFileTransformer`, as content-only loose files `MSN\<name>.MSN` and `MSN\<name>.ENG` under the install, the text taking the extension `Msn_LoadEngText` looks for in the shell's language (`.FRE`, `.GER`) (`SavedMissions`, `src/Herculan.Engine/Shell/SavedMissions.cs`). A loose file is read before any archive ([`../retail/formats/vol-archive.md`](../retail/formats/vol-archive.md#loose-files-on-disk-carry-no-prefix)), so this engine's shell and the editor load the saved mission for that name; whether VSHELL's mission load does is that doc's Open item. A replaced file is first copied to `<file>.bak`, one generation. The first save of an archive mission asks first and says that deleting the loose files goes back to the archive's.
- **Save As** takes a name of up to eight letters, digits or `_`, upper-cased, asks before replacing another mission's saved files, and renames the mission (title, later saves, the browser). A name no archive holds opens as any mission `gam\career.dat` does not list, as `INSTANT ACTION`.
- Before writing, both run the mission check over the `.MSN` ([Mission check](handoff-editor-viewing.md#mission-check)) and, when it finds anything, give the count and the first six findings as the Problems list words them, and ask Save anyway or Cancel.
- The title marks unsaved changes with `*`; the saved state is the undo history's depth and top step (`EditHistory`), so undoing back to it is clean. Before New mission or Load from VOL replaces the mission, before Back to game or Esc, and when the window is closed, the editor asks Save, Discard or Cancel; a window close is refused while it asks (`EngineWindow.CloseRequested`, which clears GLFW's close flag in its close callback).
- **File > Export script.dat** writes the generated `script.dat` and `mission.str`, the squad's `player.mec` and the `mission.var` the open wrote into a folder typed in ([The generation](#the-generation)), and refuses the install's `DATA\` and the editor's scratch folder (`HandoffExport`).

### What a saved `script.dat` reaches

VSHELL writes `data\script.dat` afresh from the `.MSN` every time it loads a campaign or practice mission, as does this engine's campaign launch (`ShellCampaignLaunch`, through `MissionGenerator`). An exported `script.dat` is therefore played by `Herculan.Engine.Host` opening that file, by DBSIM run directly over `data\`, and by a save slot, since `Career_LoadSlot` (`00412bbf`) copies `sav\script%d.dat` into `data\` and the replay plays it as-is ([`../retail/formats/save-games.md`](../retail/formats/save-games.md#the-slot-handoff)). It does not change a campaign mission, which is the `.MSN`'s; a Save of the `.MSN` does.

## Open

- **Open:** whether every retail variant table has an option whose range holds a draw of 0. A table with none makes `PickVariant` answer `-1` (`MissionGenerator.cs:306-311`), and a row-12 to 15 record that asked keeps its own refs unresolved (`:805-818`), which matters for the generation the open and Export make, every draw 0; the layout shows each table's first option whatever its range.
